### Task 1: (ai) the game-config failure memo follows the latest attempt

**File:** `src/game-config.ts` (`fetchGameConfig`), tests in the existing game-config test file(s) (find them with `grep -l "getGameConfig" tests/*.ts`).

**Problem:** `observedFailure` is set by any failed attempt (`onResponse: r => { if (!r.ok) observedFailure = true; }`) and never cleared. When a fetch sees a 503, retries, gets a 200, and is then cancelled (every caller withdrew, `signal.aborted` at the check after `sessionFetch` resolves), `fail()` records the 60 s failure memo, so config fetches are suppressed for up to a minute although the endpoint just answered.

**Fix:** `observedFailure` reflects the most recent attempt: an ok response clears it, a non-ok one sets it (`observedFailure = !r.ok`). Update the comment above the variable to say so. Nothing else changes: a fetch whose latest attempt failed and is then cancelled (e.g. during retry backoff) still records the memo; one cancelled before any failure records nothing; the deadline still records its own.

**Tests (TDD — write them first and show them failing):**
1. 503 then 200, then every caller withdraws before the result is used: no failure memo — the next `getGameConfig()` call sends a new request.
2. Existing behaviour kept: 503, then cancelled during the retry backoff: the memo is recorded (the next call within 60 s sends nothing). If an existing test already pins this, name it in the report instead of duplicating it.

### Task 2: (ag) the logged-out source index comes from the public config

**Files:** `src/game-config.ts` (`getSourceIndex` / `buildLiveSourceIndex`), tests in `tests/` (the existing source-index / game-config tests).

**Problem:** logged out, `getSourceIndex()` calls `getGameConfig()`, which with no session file sends nothing and returns null, so the index is the bundled snapshot (`src/source-snapshot.ts`). Books newer than the snapshot read "edition not stated", and `source: "<new book>"` is an unknown source — on the monster tools, which do answer logged out, and on a logged-out public character.

**Fix:** when there is no valid session (`hasValidSession()` false — no session file, a malformed or revoked one, or one with only session/expired cookies), `buildLiveSourceIndex` builds the index from `getPublicGameConfig()` instead of `getGameConfig()`. With a valid session nothing changes. `getGameConfig()` itself keeps its documented behaviour (with no session file it sends nothing).

- The `signal` contract stays: a caller whose signal aborts resolves at once to `peekSourceIndex()`. `getPublicGameConfig()` takes no signal; its fetch is shared and cached, so a withdrawn caller simply stops waiting and the fetch is left to finish (Ruling: not cancelled — it is one anonymous request, cached until the next session transition, and also what the logged-out monster path fetches anyway).
- The index cache (`indexCache`, keyed by config object identity, session-checked before caching) works unchanged with the public config object; a session transition already drops it through the module's invalidation hook. Verify that and say so in the report.
- A logged-out monster lookup must still send only the public-config request it sends today (no second, session-bound attempt).

**Tests (TDD):**
1. Logged out (no session file), a public config listing a source id absent from the snapshot: `getSourceIndex()` labels that id with its live book and category (not "edition not stated").
2. Logged out, a monster `source` naming that new book resolves (no unknown-source error) — or, if the monster tests make that heavy, `resolveSource` against the returned index.
3. Logged out, the public config fails: the index is the snapshot, `getSourceIndex()` never rejects.
4. A caller with an already-aborted / later-aborted signal gets `peekSourceIndex()` without waiting for the public fetch.
5. Logged in with a valid session: still the session-bound config (no anonymous request).

Update any existing test that pins "logged out → snapshot, no request" and list it in the report.

### Task 3: (aj) `ddb_search_site` drops sections by a structural no-match flag

**Files:** `src/tools/edition-search.ts` (`SearchSection`), every builder of a section that `src/tools/search.ts` consumes (D&D Beyond and Open5e: spells, monsters, items, races, classes, feats — find them from `search.ts`'s imports), `src/tools/search.ts`, tests in `tests/search-site.test.ts`.

**Problem:** `search.ts` judges a section empty with `EMPTY_RESULT_PATTERN` (`/^no\s+[\w\s]+?\s+found[^\n]*\.(?:\n|$)/i`) on its body, so a section whose first listed line is a closed sentence like "No Escape found." would be dropped.

**Fix:** add an optional `noMatch?: true` field to `SearchSection`. Every section builder sets it on exactly the replies that mean "nothing matched": the plain no-match reply and the hidden-only reply (search header + no-match line + footer), on both the D&D Beyond and Open5e paths. Error/unavailable replies do not set it (they are kept today and stay kept). `search.ts` drops a section when its body is empty (as today) or `noMatch` is set, and `EMPTY_RESULT_PATTERN` is deleted. The hidden-count accounting of dropped sections and every rendered reply stay byte-for-byte the same for every existing case.

**Tests (TDD):**
1. A section whose listed body starts with a line like `No Escape found.` (a real entry) is kept by `ddb_search_site` "all".
2. For each section kind used by `search.ts`, on each path it has (D&D Beyond, Open5e), the no-match reply carries `noMatch` and the listed reply does not. Use the real builders, not hand-built strings.
3. The existing search-site tests pass unchanged (the hidden-only drop keeps its count in the combined footer).

### Task 4: (al) a `source` get's note describes the book's own edition

**Files:** `src/tools/edition-search.ts` (`lookupCatalog`, `sourceFraming`), `src/tools/monster.ts` (`getMonster` with a `source`, the `sourceNote(source, shown.ruleset, requested)` call), tests in the existing catalog / monster source tests.

**Problem:** the note text is `(source "<x>" is a <edition> book — …)`, i.e. it describes the book, but the gets compute `<edition>` from the shown entry's ruleset, while searches (`sourceFraming`) compute it from the book (`sourceRuleset(source, index)`). An entry in a 2014 book whose own sources classify it 2024 (a reprint) gets a note calling the 2014 book "a 2024 book".

**Fix (Ruling: the book's edition governs on gets too — the note names the book; cost if wrong: a get's note appears or disappears for a multi-book entry):** both gets compute the note from the book's ruleset exactly as `sourceFraming` does. Factor the shared expression into one exported helper in `edition-search.ts` (used by `sourceFraming`, `lookupCatalog` and `getMonster`) rather than repeating it. The note's wording does not change.

**Tests (TDD):**
1. Catalog get (any one catalog, e.g. items or spells) with `source` = a 2014 book, an entry in that book whose own sources classify 2024: `rules_edition: "2024"` prints the note naming a 2014 book; `rules_edition: "2014"` prints no note.
2. The same pair for `ddb_get_monster` with a `source`.
3. Existing source-note tests pass unchanged.
