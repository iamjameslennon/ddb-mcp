## Two execution paths: browser vs. browserless

The central architectural split is between tools that need a Playwright browser and tools that work entirely through the saved session cookies:

**Browserless (preferred)** — `src/session-fetch.ts`
- Reads cookies from a per-user config dir — `~/.config/ddb-mcp/session.json` on macOS/Linux, `%APPDATA%\ddb-mcp\session.json` on Windows (written by `ddb_login`)
- Exchanges cookies for a short-lived cobalt JWT via `getCobaltToken()`
- All character, monster, spell, item, and condition tools use this path
- `sessionFetch()` injects the cookie header into native Node `fetch` — cookies only, no Bearer token
- `anonymousFetch()` is the credential-free path for public endpoints used while logged out (monster-service, the game config): no Cookie, no Authorization, never reads the session, the same retry policy, and a 20 s deadline (`ANONYMOUS_FETCH_TIMEOUT_MS`) over all retries and the body read
- character-service (`/character/v5/character/{id}`, `/characters/list`) ignores cookies and requires the cobalt Bearer token — use `beginAuthenticatedSession()`, whose bound `fetch` sends the token and cookies from one snapshot. Never pair a separate `getCobaltToken()` with `sessionFetch()`: each captures its own snapshot, so an account swap between them can send one account's token with another's cookies
- Every credential access binds to a `SessionSnapshot` from `src/session-state.ts` (see **Revocable session lifecycle** below) and re-checks on-disk authority before dispatch — a deleted/replaced session file, or a `ddb_logout` revoke, stops the old account's credentials at the next protected operation with no explicit invalidation call required

**Browser-based (Playwright)** — `src/browser.ts`
- Required for: `ddb_login` (OAuth flow, visible window), `ddb_navigate`, `ddb_interact`, `ddb_get_page` (every other tool is browserless — see [Browser dependencies](#browser-dependencies))
- Singleton browser/context (`getBrowser` / `getContext`) — lazy-initialized, shared across calls, bound to the generation they were opened under (an `onSessionInvalidated` hook closes and detaches the shared context/browser on every session transition, including a `ddb_logout` revoke — `revokeSession()` awaits that close and reports if it fails)
- `ddb_login` forces `headless: false`; all other browser tools use `headless: true`
- navigate/interact/get_page leave the browser open intentionally; `ddb_close_browser` (or process shutdown in `index.ts`) closes it
- Login uses a deliberately separate browser/context (`beginLoginSession()`/`endLoginSession()`) from the shared authenticated one, so a login can't reuse a possibly-revoked context and a revoke mid-login can't be raced into recreating a just-deleted session (`saveVerifiedSession()` re-checks the generation it began under, before and after its async storage read)
- The login context is seeded from the `captureSession()` snapshot that `beginLoginSession()` takes (its sanitized `dndbeyond.com` cookies, no origins), only when that snapshot is `authenticated`; anonymous or `revoked` seeds nothing. It never reads `session.json` by path, so a logout whose file deletion failed can't bring the revoked cookies back through the login window (Task 10b, investigation §3). The shared context's `buildContextOptions()` still loads the file by path
- Login ownership: `ddb_login` calls `endLoginSession(context)` only when its own `beginLoginSession()` succeeded, so a second concurrent call answers `A login is already in progress…` and never closes the first's window; `endLoginSession(context)` ignores a context that isn't the current login's, and closes the browser even when closing the context throws (the first error is rethrown)
- **Sign-in is verified by D&D Beyond, not the page** (`src/auth.ts`, Task 10b, F30/F29). `login()` first asks whether the seeded context is already signed in, then opens `https://www.dndbeyond.com/login` and polls every 2 s (`LOGIN_POLL_INTERVAL_MS`) until a 180 s deadline (`LOGIN_TIMEOUT_MS`, measured from the start of `login()`). Each poll is `verifyLoginContext()`: a POST to `https://auth-service.dndbeyond.com/v1/cobalt-token` through `context.request` (it shares the context's cookie jar), with a per-request timeout of at most 10 s. Only a token that `decodeCobaltToken()` (shared with `mintCobaltToken` in `session-fetch.ts`) accepts counts; `{"token":null}`, a non-OK status or an unusable token mean "not yet", and a network error is logged to stderr once per distinct message and also read as "not yet". The proof (`VerifiedSignIn`) is bound to its context in a `WeakMap`, and `saveVerifiedSession(context, proof, signal)` refuses anything else, so an anonymous cookie set is never saved; there is no unverified `saveSession()` any more. The old URL predicate (whose options were passed as `waitForFunction`'s `arg`, so Playwright's 30 s default applied) and the `UserNavigation` DOM heuristic (which matched the anonymous Sign-in link) are gone
- What ends a login early (`LoginWatch` in `auth.ts`), each raced against every wait: closing the last sign-in window (pages and popups are tracked through the context's `page` event; a Google popup closing while the main window stays is not an end), the context's `close`, the browser's `disconnected`, a Playwright "Target page, context or browser has been closed" error, and the request's cancel signal (`extra.signal`). The save itself isn't raced: `saveVerifiedSession` checks the signal after its async storage read and before the write
- `ddb_login` sends `notifications/progress` (`progress` = seconds waited, `total` = 180) every 10 s (`LOGIN_PROGRESS_INTERVAL_MS`) when the request carries `_meta.progressToken`, so a client that resets its request timeout on progress (the SDK client default is 60 s) keeps the call alive; the interval is cleared when the call ends

## Revocable session lifecycle — `src/session-state.ts`

Owns the single authoritative answer to "which account are we, right now?" and sits below every other module (never imports a tool module). A "generation" is an opaque, process-local, monotonically-increasing token; two `SessionSnapshot`s share a generation iff they describe the same on-disk session-file content. `captureSession()` re-reads the file on every call — this re-read, not a file watcher or mtime check, is what makes deletion/replacement/corruption observed at the next protected operation. A file that parses but isn't a storage state (JSON `null`, an array, a number or string, or an object without a `cookies` array) is `anonymous` with reason `malformed`, like unparseable JSON, so tools say to run `ddb_login` rather than send requests with no credentials (an object with an empty `cookies` array is still a session). Every rewrite of the file (`writeSessionFile`: the third-party scrub and `saveSession()`) first removes, best effort, `session.json.<pid>.tmp` files left by a writer that crashed between its write and its rename: only when the pid is not this process, no such process is running (`process.kill(pid, 0)`), and the file was last modified at least 10 s ago (`TEMP_FILE_MIN_AGE_MS`: a writer in another PID namespace reads as dead), so a live writer's temp file is never touched; a failing sweep never fails the read or the write. Any observed change advances the generation, aborts in-flight work (via `AbortSignal`), detaches cached state, and fires every callback registered with `onSessionInvalidated()` (session-fetch's cobalt-JWT cache, `browser.ts`'s shared context/browser, and each tool module's account-derived cache all register one).

`revokeSession()` — the primitive behind `ddb_logout` — blocks new authenticated operations immediately (`revoked` flag, checked before any file read), invalidates in-memory state, deletes the saved session file (`rmSync(..., { force: true })`, ENOENT-safe), then `Promise.allSettled`s every registered async cleanup hook (currently just the browser close) before resolving. Repeated calls are idempotent. If file deletion or a cleanup hook throws, `revokeSession()` still leaves the process-local `revoked` flag set — no old-file reload, no silent "logout succeeded" — and rejects with an `Error` naming which step failed. A subsequent `ddb_login` clears the flag via `invalidateSessionCache() → clearRevoked()`, establishing fresh authority. See [README's Logging out section](../../README.md#logging-out) for the user-facing guarantee and its limits (detection is at the next protected operation, not instantaneous; stop the process for immediate termination).

**Future design note:** any later stateless-safe/browser-factory redesign must adopt this same lifecycle rather than reinvent it — factory-created browsers need to bind each created context to a captured `SessionSnapshot` and register the same kind of `onSessionInvalidated` revocation hook `browser.ts` uses today, and any future on-disk cache (e.g. a persisted spell compendium) needs a durable per-account/session key plus validation at read time, not the in-memory `generation` counter alone — it's process-local and resets on restart, so it cannot identify which account a given disk-cache entry belongs to across process restarts.

Open5e silently ignores every filter it doesn't know (`search`, `name__icontains`, `challenge_rating_decimal`, …; `document__key` is ignored by `items` and `magicitems`), so the only request shape is a whole document per endpoint (`?document__key__in=<doc>&limit=1000`, `next` followed defensively, any record from another document dropped by `docKey`) and every match is client-side. Spells, creatures, items, species, classes, backgrounds and feats load **both** documents in parallel and select together through `lookupByName` (gets) / `groupAndSelect` (searches) with each record's ruleset taken from its document, so Open5e answers follow the D&D Beyond pipeline: 2024 by default, a 2014-only entry tagged `[2014]`, other-edition twins hidden and counted. Equipment is one exact-first `o5GetEquipment` across items, magicitems, weapons and armor. Open5e searches open with `open5eSearchHeader` (their lines mix SRD 5.2 and 5.1). Rules come from `/v2/rulesets/` (chapters nesting their sections), not twin-grouped: the requested SRD first, then the other. Names go through one Open5e twin namer per rename kind (`o5TwinNameFor(endpoint)`: spells → `spell`, creatures → `monster`, items/magicitems/weapons/armor → `item` plus the Open5e-only `OPEN5E_ARMOUR_RENAMES` and `OPEN5E_EQUIPMENT_RENAMES`, that key folded further by `o5EquipmentKey` (M1–M3: `+N` as `plusN`, punctuation as spaces, words sorted, `sword`/`weapon` dropped, a price, count or measure in parentheses, a category prefix and `set` stripped, one trailing `s` per word; carry-over (r)), backgrounds → `background`, classes → `subclass` (Open5e files subclasses on `/classes/`; owner ruling 2026-10-29), species/feats/rulesets → none — each with `-` folded to a space and straight and curly apostrophes dropped on both sides, in the key and in every Open5e name filter (owner ruling 2026-10-21: `will o wisp` finds Will-o'-Wisp; rename lines keep the records' own spellings), so SRD 5.1's "Adamantine Armor (Chain-Mail)" twins SRD 5.2's "Adamantine Armor (Chain Mail)"; D&D Beyond's `twinNames` do not fold); rename lines are suppressed when the shown entry carries the other edition's spelling (SRD 5.2 keeps 2014 names for 30 pairs, so `Bigby's Hand` shows `Arcane Hand` with no rename line) and when the names differ only by a hyphen, an apostrophe, word order or, for equipment, a part the M3 strip removes (`sameWords`: the same twin key and the same words of `o5Folded`, for equipment after the M3 strip of a price, count, measure, category prefix, `set` and stray `)`; commas, other parentheses and plurals count, so `Crossbow, hand` → `Hand Crossbow` and `Arrow (bow)` → `Arrows (20)` keep their lines while `Smith's tools` → `Smith's Tools (20 GP)`, `Bagpipes` → `Musical Instrument, Bagpipes`, `Acid (vial)` → `Acid` and `Three-Dragon Ante Set` → `Three-Dragon Ante` have none; owner ruling 2026-10-30), and when the other document files the shown name too (no line when the other edition also has a record of the shown name). Two records of one SRD document never share a twin group through the equipment folds alone (`guardedNamer`, whose split is computed once over all four equipment endpoints' records in both documents and cached with them, so a search and a get agree: such a key splits by rename-table key, so SRD 5.2's "Potion of Healing" and "Potions of Healing" stay two entries; owner ruling 2026-10-30). A search, like a get, picks the record whose name is the exact query within a group (`Acid (vial)` under 2014 lists SRD 5.1's "Acid (vial)", not its group's "Acid"). A species or class search given a name, or any background or feat search, with one hit renders the detail block with the single-lookup label (`o5OptionReply`), not the search header, plus the rename line a get of the query would print (same lookup, same suppression; kept only when it shows the same entry). 1 h TTL cache, one in-flight fetch per URL, a 20 s timeout per request inside one 30 s deadline per document (`O5_DOCUMENT_DEADLINE_MS`, `AbortSignal.any`), and a response is rejected when it is off-origin (a redirect, checked on `resp.url`; an empty `url` is rejected too: `Open5e response has no final url: <path>`), has no records, or reports a first-page `count` above the raw records collected (before the document filter); a failure is never cached as data but is remembered for 60 s per URL (`O5_FAILURE_TTL_MS`, rethrown without fetching; `clearOpen5eCache()` and `ddb_clear_cache` drop it, and a fetch superseded by a clear writes none); if either document fails to load, the whole call fails: content-fallback callers print their existing "… D&D Beyond and Open5e both failed." messages, the rules tools (Open5e-primary) throw and `server.ts` answers `Rules search failed: …` / `Rules lookup failed: …`, and `o5GetMonsterStats` returns `unavailable` for it (a genuine miss is `not-found`), and `getMonsterStats` turns that into `unavailable` only when D&D Beyond could not be asked either, else `not-found` (encounter and treasure then print "Couldn't look up — D&D Beyond unreachable" or "not found"). Stores parsed objects (not JSON strings). |

## Browser dependencies

All content tools are now browserless. `ddb_search_site` ([search.ts](../../src/tools/search.ts)) delegates to the cached compendia in `reference.ts` / `monster.ts`. `ddb_list_library` ([library.ts](../../src/tools/library.ts)) parses the library page's embedded RSC payload (`self.__next_f.push(…)` chunks) from `sessionFetch` HTML. `ddb_read_book` fetches sourcebook pages via `sessionFetch` and walks the `<article>` tree with cheerio — DDB book chapters are server-rendered, so no JS execution is needed.

The only tools that still drive a browser are `ddb_login`, `ddb_navigate`, `ddb_interact`, and `ddb_get_page` — all inherently browser-bound (OAuth flow / live page interaction).

Browser contexts used by navigate/interact/get_page carry a navigation guard (`ensureNavigationGuard` in [navigate.ts](../../src/tools/navigate.ts)): top-level navigations to non-allowlisted hosts are aborted at the network layer, `interact` re-checks `page.url()` after every click, and `getCurrentPageContent` refuses to scrape any page outside the allowlist (covers data:-URL navigations, which never hit the network layer). The `ddb_login` context never passes through these functions, so the Wizards SSO redirect flow stays unguarded.
