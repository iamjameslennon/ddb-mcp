# Tool behaviour reference

> Moved verbatim from `CLAUDE.md` on 2026-11-06 to keep that file lean. `CLAUDE.md` keeps the summary and links here; this file holds the full detail. Keep it current when behaviour changes.

## Tool notes

- `ddb_get_character` accepts a `sections` param — prefer `summary` or `combat` over `full` to save tokens. Every section opens with a `Rules:` line right after the character's name, which is wrapped as untrusted, so the Rules line follows the closing tag (part of `formatHeaderBlock`), and entries whose ruleset differs from the main edition carry an inline tag (see the Rules edition bullet under parseCharacterData notes). Character tools take no `rules_edition` and do no twin selection
- `ddb_character_lookup` tags every list line (the >3-hit list) with `editionTag` and gives every full hit a `rulesLine` under its first line, from the character's `CharacterEditions.info()` (so a Dagger on a 2014 character reads `Rules: 2014 · Basic Rules (2014)`). A homebrew hit (or a custom background's feature) is wrapped in `wrapIfHomebrew` / `wrapUntrusted`: the whole block, rules line included, or the whole list line, tag included. Class and subclass features take the owning class's or subclass's definition, racial traits the species, the background feature the background. No reason lines: character content has no requested edition. An item hit's name is trimmed (in the full hit and the list line). A custom item (`definition.isCustomItem === true`) reads `Rules: custom item` (`CUSTOM_ITEM_RULES_LINE` in `src/edition.ts`) instead of its ruleset's line, and stays wrapped through `isHomebrewEntry`; its line in the >3-hit list carries no edition tag, as on the sheet, and stays wrapped (owner ruling 2026-11-07). An item hit whose ruleset (`info.ruleset`, the one its Rules line names, never re-classified) is 2014 drops the description's 2024 mastery paragraph through `withoutMasteryParagraph` (`src/tools/weapon-mastery.ts`, shared with `ddb_get_equipment`); the lookup prints no property list, so there is nothing else to drop (owner ruling 2026-11-06). A spell's name falls back to the entry's `name` when its definition has none, and class spells are read from `classSpells[].classSpells` as the sheet does (it used to read only `spells`)
- `ddb_get_party` prints each member's `summary` section, so the header carries the `Rules:` line and the class, subclass, species and background tags; the head `Rules: edition not stated` covers unstated feats, spells and items there (carry-over (c), closed)
- `ddb_get_character_raw` returns raw 300–500 KB JSON and requires `confirm_large_response: true`
- `ddb_character_lookup` returns a summary list when >3 matches — refine the query to get full text
- **Lookup name matching and subclass features** (F2, F9; owner ruling 2026-11-12): `ddb_character_lookup` matches names with `matchesLooseName` (`src/name-match.ts`): the folded query is a substring of the folded name (apostrophes and hyphens folded), or the query has at least one word of 3+ letters (ignoring of/the/a/an) and every such word is within edit distance 1 (word up to 4 letters) or 2 of some word of the name, so typos and word order are tolerated ("eldrich blast", "trickster blessing"). A query with no 3+ letter word ("ki", "of the") matches by substring only; an empty folded query never matches. `levenshteinDistance` lives in `name-match.ts` (re-exported from `helpers.ts`). A feature in `classes[].classFeatures` whose `definition.classId` equals the subclass's `id` is a subclass feature (`isSubclassFeature` in `definition.ts`): it is a `[Subclass Feature]` hit labelled `Class / Subclass` with the subclass's book, and a chosen option under it with no source of its own falls back to the subclass's book and the same label.
- `ddb_search_spells` / races / classes / backgrounds / feats / class_features / racial_traits all accept `limit` and `offset` for pagination
- **Open5e option-search fallbacks** (races, classes, backgrounds, feats) honour `limit` and `offset` (default 30/0), and the feats one honours `prerequisite` (`prerequisiteMatches`, `src/tools/prerequisite.ts`, shared with the D&D Beyond feat search: every query word is among the prerequisite's words in any order, with str/dex/con/int/wis/cha expanded, or the lower-cased query is a substring of it, on the text with its "Prerequisite:" prefix stripped; a feat with none never matches). The heading is `Found N feat(s) (SRD only):` when the page shows all N, else `…, showing A–B:` (offset > 0 included) with `*Use offset: B to see more.*` when more remain; an offset at or past the end is `Found N … (SRD only) — offset X is past the end.` (not the no-match reply). N counts every match; a single hit is still its detail block (owner ruling 2026-11-06)
- **Phase-3 tools** (`ddb_get_equipment`, `ddb_search_equipment`, `ddb_search_races`, `ddb_search_classes`, `ddb_search_backgrounds`, `ddb_search_feats`, `ddb_search_class_features`, `ddb_search_racial_traits`) take `rules_edition` (default `"2024"`) and `source`; `ddb_get_spell` / `ddb_search_spells` also take `source`, and `ddb_search_site` takes `rules_edition` only. `source` (slug, short name or title, resolved through `getSourceIndex()` to every matching id; `"homebrew"` is reserved and lists homebrew entries only, as on the monster tools) wins over `rules_edition`: no twin hiding, every entry in the book is listed with its tag, the header is `searchHeader({ sourceBook })`, and a `sourceNote` is added when the book's edition contradicts `rules_edition` (a get instead notes only when the shown entry's edition differs from `rules_edition`: `lookupSourceNote`, carry-over (ap)). Every search with results from D&D Beyond starts with its search header, then any note, then the tool's heading; the tag sits right after the bolded name (`- **Fighter** [2024] — …`); header totals and the footer ("N 2014 versions hidden — rules_edition: \"2014\" shows them") count the whole result after hiding, not just the page. In flat mode (spells, items, classes, backgrounds, feats) a twin group whose requested-edition pick fails the filters while the other edition's pick passes is not listed but is counted in the footer, once per group (`groupAndSelect`'s `countFilteredPicks`; monster search sets it too); when that leaves nothing listed, the reply is the search header, `No <kind> found matching the criteria.` and the footer, not an Open5e fallback.
- **`ddb_get_equipment` and 2024 weapon mastery**: when the shown entry's ruleset (`found.info.ruleset`, passed to `formatItem`, never re-classified because a dual-edition definition would classify as 2024) is 2014, `Properties:` omits the `MASTERY_NAMES` (`src/tools/weapon-mastery.ts`) and the description is cut at the paragraph that starts `This weapon has the following mastery property`, trailing whitespace trimmed (`withoutMasteryParagraph`, shared with `ddb_character_lookup`). A 2024 reply is unchanged. The Open5e fallback is not touched.
- **Dual-edition items** (`ddb_get_equipment`, `ddb_search_equipment`, and the items section of `ddb_search_site`; decision 4, the rule character sheets use): a non-Legacy, non-homebrew item definition that lists a 2024 book and a 2014 book (539 live, e.g. Longsword, Studded Leather) is classified as the requested edition, with that edition's first book; a book's ruleset is `sourceIdRuleset(sourceId, categoryId)` in `src/edition.ts`: the per-source override (`SOURCE_RULESET_OVERRIDES`, B12), then the book's category (`classifyForEdition` in `src/edition.ts`, via `CatalogAdapter.dualEdition` in `edition-search.ts`). Under a `source` the book's edition decides when it is 2024 or 2014 (`source: "basic-rules-2014"` tags Longsword `[2014]`), else the requested edition. A dual item alone in its twin group (537 of 539) is shown under either edition with no reason line and is never counted as hidden. A non-dual entry of the requested edition beats a dual one (owner ruling 2026-10-28, option B): when the dual item's twin group holds one (the 2 live groups: Legacy Efficient Quiver with Quiver of Ehlonna, and Legacy and dual Robe of the Archmagi), the dual item classifies as `classifyEdition` does, so those groups print what they did before (`Efficient Quiver` under 2014 is the Legacy printing, `Rules: 2014 · Basic Rules (2014)`, with a "1 2024 version hidden" footer in search). Under a `source`, B looks only at the book's entries (B within the book, owner ruling 2026-10-29): the book's edition decides except where the Legacy twin is in the same book, so `source: "dmg-2014"` (which lacks Efficient Quiver) tags Quiver of Ehlonna `[2014]`, while under `basic-rules-2014` (which holds both Robes) the dual Robe stays `[2024]`. B counts only entries that pass the search's filters (under a `source` also the name filter, since that listing filters entry by entry): when a filter rejects the Legacy twin and passes the dual item, the dual item is listed with the requested edition's tag and is not counted as hidden. B tracks entries, not marker objects (`classifier()` in `edition-search.ts`). A dual pick's book note names its book in the requested edition. Item dedupe falls back to `entityTypeId:id`, then (both missing) to the id with the normalized name and filterType.
- **Book-choice note**: when one edition has several versions of an entry (a book owner's 2014 Goblin from Volo's and from Monsters of the Multiverse), the pick is official → non-Legacy → lowest id. Search lines name the book and the set-aside books (`· <book> (also in <book> — pass source to choose)`); a single get adds an "also in" line. For class features and racial traits the note goes on every line of a duplicated owner. Only set-aside versions that pass the search's filters count. `ddb_search_site` has no `source` param, so its sections omit the note (`bookNotes: false` → `SelectOptions`); lines keep their tag.
- **Class features and racial traits choose the edition per owner** (class, class + subclass, or species), not per feature, and filter first: under 2024, `class_name: "ranger"` lists only the 2024 Ranger, with the 2014 owner's features hidden and counted (no Natural Explorer, Primeval Awareness, Vanish); `name: "natural explorer"` finds `Natural Explorer [2014]`; Fighter `name: "ability score"` lists the 2024 lines (including level-prefixed ones like `6: Ability Score Improvement`) plus a hidden footer. Species group by base race: the 2024 Elf replaces the 2014 High Elf, Wood Elf and Eladrin (Variant) in `ddb_search_races` and `ddb_search_racial_traits`; `rules_edition: "2014"` lists each subrace; naming it (`race_name: "high elf"`) finds `High Elf [2014]` under either edition. A 2024 Bard who is a 2014 High Elf is served by naming the species, a per-call `rules_edition`, or `source`. Without `source`, results list the requested edition's owners first, then the other edition's (a 2014-only Samurai after every 2024 Fighter line), then third-party/homebrew/unstated owners, each band in the usual feature/trait order; species searches and the flat catalogs keep their plain order. In every mode, with or without `source`, entries that tie on that order (equal names: a 2024 "Tiefling" and a homebrew "Tiefling" subrace) are listed by the adapter's tiebreak, official → non-Legacy → lowest id.
- **`ddb_search_site`** with `category: "all"` prints one search header and one combined footer: each category contributes its `SearchSection` body, and the header appears only when at least one included section came from D&D Beyond. An Open5e section (`open5e: true`; built by the `o5Search*Section` siblings in `src/open5e.ts`, whose string wrappers `o5Search*` render them unchanged) keeps its own `Rules:` line (its header, or a single-hit detail block's own label) above its body, so an all-Open5e reply has no combined header. A monster near-match section (`ownRulesLine: true`) likewise keeps its own neutral `NEAR_MATCH_RULES_LINE` (or the homebrew form) above its body and does not count towards the combined header (A1, owner ruling 2026-11-10). The combined footer counts the hidden twins of every section, D&D Beyond or Open5e, listed or dropped; no section prints its own footer, so a listed Open5e section's own hidden line moves into it (owner ruling 2026-11-02). A single category keeps its own header and footer. A section whose body is empty or that carries `noMatch` (never judged by its text) is dropped, including a hidden-only one, whose count still reaches the footer. When every section is dropped, the reply is `No results found for "<query>".`, followed by a blank line and the combined footer when any section hid twins (owner ruling 2026-11-02).
- `ddb_get_spell` / `ddb_search_spells` take `rules_edition` (default `"2024"`). Both editions are in the compendium (keyed by definition id); get shows the requested edition's spell with a `Rules:` line, or the other edition with a "no 2024/2014 version found" reason, and a rename line when the query used the other edition's name (`Acid Arrow` → Melf's Acid Arrow). Search hides the other edition's twins and tags each line. A get by partial name (`ddb_get_spell`, `ddb_get_equipment`) that matched one twin group while other groups also match the query at a word start (`matchesAtWordStart`) adds `Also matches: A, B, … Ask for one by name.` right after the Rules lines (`LookupResult.alsoMatches`, set only on the partial path; up to 5 names A–Z, then `, and N more`; `alsoMatchesLine` in `edition-search.ts`; wrapped whole as untrusted when any listed name is homebrew). The D&D Beyond feat search's `prerequisite` uses the same `prerequisiteMatches` ("Strength 13" lists "Str or Dex 13+"; `countFilteredPicks` hidden counts are unchanged, so a twin that also passes is still counted hidden, F21), merges hits with an identical name and tag into one row ending ` ×N` (counted once in the total; "Magic Initiate (Cleric)" and "(Wizard)" stay apart, F23), and its snippets (all option searches' descriptions, via `clip`) put a space at each block end and `<br>` (F20).
- `ddb_get_spell` and `ddb_character_lookup` print `Casting Time:` through `castingTimeText` (`src/tools/casting-time.ts`), the one map of DDB's `activationType` (1 Action, 2 No Action, 3 Bonus Action, 4 Reaction plus `castingTimeDescription` as the trigger, 5/8 Special, 6 Minute, 7 Hour; other types print `N (activation type T)`). The label is plural when N is not 1; a missing or zero N counts as 1 and an absent `activation` reads `1 Action`. Before this, types 4 and 7 fell back to "Action" and 6 was labelled "Reaction". `actions.ts` still filters on the raw numbers.
- `ddb_search_rules` / `ddb_get_rules` — SRD rules search and retrieval, no login required. Both take `rules_edition` (default `"2024"`: SRD 5.2; `"2014"`: SRD 5.1). They read Open5e `/v2/rulesets/` (SRD 5.2: 11 chapters, SRD 5.1: 41, each nesting its sections), so a get takes a chapter name or slug (`Combat`, `combat`) or a section name (`Cover`, `Grappling`) and a chapter returns all its sections. A slug is the key after its first `_`. A get matches in the requested SRD first (exact chapter, exact section, partial chapter, partial section), then the other SRD with `(no matching 2024 rules section — 2014 text shown)`. A search lists matching chapters, naming matching sections, each tagged `[2024]` / `[2014]`, and when the requested SRD has no match lists the other SRD's under `(no matching 2024 rules sections — 2014 sections listed)`. Query and text are folded like `normalizeName`; a blank get name is not found and a blank search query lists every chapter. Search matches whole words, not substrings (`wordPhraseIndex`: the query as a phrase on word boundaries, an optional plural `s`/`es`; "cover" no longer lists Madness for "discovered", F16), and a get's `query` jump uses the same index. Every text a get prints goes through `cleanO5Markdown` (output only, never matching; F15): `srd:fire-bolt` links become `fire bolt`, `---` between two words becomes an em dash (table separator rows and horizontal rules are untouched), adjacent `**a** **b**` runs merge, and the one upstream Open5e typo found, `HalfCover` in the srd-2024 rulesets, becomes `Half Cover`. A get whose `query` is not in the text keeps the section's start and adds `*"<query>" not found in <section or chapter> — showing its start. Try ddb_search_rules.*` after the `Rules:`/`Part of` lines. An Open5e per-request timeout (20 s) reads `Open5e (api.open5e.com) didn't answer within 20 s — try again shortly.` (remembered 60 s like any failure). SRD 5.2 on Open5e has no Rules Glossary, so a 2024 `grapple` search falls back to 2014, and no spellcasting chapter, so a 2024 get of `spellcasting` returns the Spellcasting section of Multiclassing (the 2014 chapter needs `rules_edition: "2014"`). v1's 2014 Adventuring Gear, Conditions, Legal Information and Rest chapters no longer exist on this path
- `ddb_get_condition` takes `rules_edition` (default `"2024"`): the 2024 text is SRD 5.2.1 (`Exhaustion` is the 2024 text, with D20 Tests reduced), `"2014"` gives the six-level Exhaustion table. Both lines read `Rules: 2024 · SRD 5.2` / `Rules: 2014 · SRD 5.1`; there is no reason line or fallback, because both tables are vendored; an exact key wins, a partial name matching several conditions answers `Condition "ed" is ambiguous: … — use the full name.` (table order), and a unique partial resolves
- **Open5e fallbacks are final** (phase 4): every single lookup and single-hit detail block is labelled by its document's ruleset (`Rules: 2024 · SRD 5.2 (Open5e fallback — D&D Beyond unavailable | not found on D&D Beyond)` / `SRD 5.1`), with the usual reason line when the edition differs, while Open5e searches open with `open5eSearchHeader` and tag each line `[2024]` / `[2014]`; the interim `Rules: 2014 · SRD 5.1 (Open5e fallback — …)` label on every fallback is gone. An exact twin name in one SRD beats a partial match in the other, as on the D&D Beyond path, so `Rope` under 2014 gives SRD 5.2's Rope with `(no 2014 version found — 2024 text shown)` though SRD 5.1 has "Rope, hempen (50 feet)". Open5e `getMonsterStats` (`o5GetMonsterStats`) mirrors the D&D Beyond branch: exact twin name first, else partial matches grouped by twin key; one group is `found` (picked by edition), several are `ambiguous` with one candidate per group by CR then name, so a logged-out `Red Dragon` lists five candidates (Red Dragon Wyrmling, SRD 5.1's 2014-only Half-Red Dragon Veteran, Young, Adult and Ancient Red Dragon) and `Ancient Red` is found. Open5e monster blocks show recharge, per-day and legendary costs on action names, print `LEGENDARY_USES_NOTE` (`src/edition.ts`) on the line after `LEGENDARY ACTIONS` (v2 has no per-round count), and do not print v2 `subcategory`. `o5GetMonsterStats` selects the edition over every name match first; a picked record with an unknown CR is `not-found` for an exact or single-group match, never replaced by its other-edition twin; in an ambiguous list it stays, printed `<Name> (CR unknown)` (`CR_UNKNOWN_TEXT`, `src/edition.ts`) and sorted last, and when every pick is unknown the answer is `not-found`. `ambiguityMessage` (both paths) names at most `AMBIGUITY_LIST_CAP` (20) candidates in the caller's order (CR, then name), then `, and N more`. Open5e `school`, `type` and `size` match part of a word, untrimmed (so a whitespace-only query matches nothing), as on D&D Beyond; `rarity` stays exact and is trimmed on both paths; null `rarity` / `category` on an item record are tolerated (no empty parentheses; a magic item with a null rarity counts as Common). Open5e species searches group by base race, as D&D Beyond does. Seven armour renames (Leather, Padded, Studded leather, Hide, Half plate, Splint, Plate → "… Armor") apply to Open5e only
- **Open5e output details**: reaction spells show `reaction_condition` after "1 reaction", and `Duration:` is capitalized ("Instantaneous"); an item search with no match says "No items found matching the criteria on D&D Beyond or in the SRD." (origin `not-found`; `(SRD only).` when D&D Beyond was unreachable, origin `unavailable`; the same suffix rule covers spells, species, classes, backgrounds and feats, via `o5NoMatch`). `ddb_get_spell` / `ddb_get_equipment` with no match anywhere say `<Spell|Item> "X" not found on D&D Beyond or in the SRD. It may be misspelled, or in a book this account doesn't own (D&D Beyond shows only free content and owned books). Try …` (the compendium holds only visible entries, so locked and absent can't be told apart). `source: "br-2024"` on the spell, feat, species, class, background, class-feature and racial-trait tools returns `basicRules2024Reply` (`source-filter.ts`, owner ruling R4, 2026-11-11): a redirect to `phb-2024`; items and monsters never call it (items carry source 148) and a mundane item line is `• <name> [tag] (<category>)`; class `Features:` lists only `feature_type` CLASS_LEVEL_FEATURE; within the edition `selectByEdition` picks, an exact name beats endpoint order ("Plate Armor" under 2014 gives the SRD 5.1 items record); a weapon or armour get ends with its `items` twin's `Cost: … | Weight: …` line (same document, same Open5e twin key) when there is one; species and background detail blocks print the record's `desc` (SRD 5.1 only; SRD 5.2's are empty) before the traits or benefits; monster and item searches list 20 lines, then `*Refine your search to see more results.*` before the footer, as D&D Beyond's item search does; `rarity` matches exactly on both paths (`common` is not `Uncommon`), and mundane gear counts as Common (D&D Beyond: an item with no rarity; Open5e: every `items` record), so `rarity: "common"` lists mundane gear plus Common magic items; the `ddb_get_rules` `query` jump folds case, curly apostrophes and whitespace as the rules search does, keeping the original text; an ambiguous `ddb_get_condition` name lists at most 20 (`cappedList` in `src/edition.ts`, then ", and N more"; 15 conditions never reach it); `ddb_get_condition` matches only its own table keys (`constructor` is not found) and a blank name is not found
- `ddb_search_class_features` `class_name` matches the class or the subclass name (`champion` finds Champion features). Each owner gets its own entry, so a racial trait shared by a base race and its subraces (e.g. Darkvision under both High Elf and Wood Elf) is listed once per species — with `rules_edition: "2014"`, or when the subrace is named (`race_name: "high elf"`); by default the 2024 species hides the 2014 subraces of the same base race. A locked optional entry (`accessTypes` 4) is listed with a "locked — not available to this account" marker instead of text. When D&D Beyond returns no class or race data the tool errors with "… data is unavailable from D&D Beyond right now …"; "No class features / racial traits found matching …" means the data loaded and nothing matched, and ends with a reminder that D&D Beyond lists only the classes, subclasses and species available to your account, so an absent class or species may just be locked. `ddb_search_racial_traits` `race_name` also matches a subrace's base race: with `rules_edition: "2014"`, `elf` also finds "Eladrin (Variant)", a subrace of Elf (under the 2024 default the 2024 Elf replaces it, and the subrace is found by naming it)
- `ddb_read_book` defaults to 3000 chars; use `query` to jump to a specific heading. A `Rules:` line (`rulesLine` of the book's join, e.g. `Rules: 2024 · Player's Handbook (2024)`) sits between the `# <slug>` title and the `URL:` line; a book that doesn't join is `Rules: edition not stated`
- **Unowned-book note (F17)**: every `source` search on the catalog tools (spells, equipment, species, classes, backgrounds, feats, class features, racial traits; not `homebrew`, not the `br-2024` redirect, not gets) puts `> Note: this account doesn't own <book>, so D&D Beyond shows only its free entries — this list is not the whole book.` first in the body, found or not, before the `sourceNote`. It is `unownedSourceNote` in `library.ts`, applied by `withUnownedNote` in `reference.ts` around `searchSpellsSection`, `searchCatalogList` (also behind the option lists) and `searchOwnedEntries`. It reuses the cached library list (`fetchLibraryBooks`, so the session-lifecycle and cache rules apply) and joins each library book with `librarySourceId`. No note when logged out (no fetch), for a free book (`isFreeBookSlug`: `basic-rules-2014`, `br-2024`; no fetch), when any library book joins one of the source's ids, when the fetch throws or parses empty (only `SessionChangedError` propagates). The old (B14) "No spells found" carry-over is closed by it.
- `ddb_list_library` stays JSON: each book gains `"edition": "[2024]"` (the `editionTag` text; `[edition not stated]` when the join fails). **Library join** (`librarySourceId` in `library.ts`): (a) the slug's non-empty path segments are tried right to left, each against the last non-empty segment of a source's `sourceURL`, and the first segment with any candidate decides the step (a pick, or a disagreement that falls through to (b); later segments are not tried), so a chapter path `dnd/phb-2024/creating-a-character` joins on `phb-2024` (`dnd/phb-2024` → `phb-2024`; a slug or `sourceURL` with no segment, `""` or null, never matches, because 57 sources have `sourceURL: ""`); (b) else the normalized title equals a source's normalized decoded `description` **or its book label** (`Player's Handbook (2024)`). Within a step the candidates are classified with `classifyEdition({ sourceId })`: non-`unstated` candidates that share one ruleset give the lowest id among them (`basic-rules-2014` is ids 1, 209, 210, 212, and 1 is the labelled one, so a Hidden Sources twin never wins); with no non-`unstated` candidate, the lowest id; if they disagree the step fails. Both steps failing is `{ ruleset: "unstated", book: null }`. `ddb_read_book` given a slug runs (a) only; when that fails and the title is unknown it fetches the library list once, takes the title of the library book whose slug equals the path or is a leading path prefix of it (the longest match wins; books with an empty slug are skipped) and runs (b). A slug missing from the library, or a failed library fetch, leaves the book "edition not stated" and never fails the read. Live 2026-10-23: 8 of 8 library books join by slug
- `ddb_rate_encounter` / `ddb_encounter_cr` accept `rules_edition: "2024" | "2014"` (default `"2024"`) for XDMG vs. classic DMG rules; `"2014"` also resolves named monsters' CRs from their 2014 stat blocks. Line 2 of the output is the `Rules:` line for that edition's Dungeon Master's Guide (`DMG_SOURCE_ID` in `src/edition.ts`), and each named monster carries an edition tag (`1 × Wolf [2024] (CR 1/4, 50 XP)`; a `cr`-supplied one has none). When a named monster went uncounted (not-found, unavailable, ambiguous or unknown-CR; `m.count ?? 1` each, so `{name:"Nope", count:3}` is 3; an entry with neither name nor cr stays silently skipped, owner ruling 2026-11-06) and something else counted, the headline is `ENCOUNTER DIFFICULTY: INCOMPLETE — N monster(s) not counted (the rest rate <DIFFICULTY>)` (2024 keeps its ` (2024 XDMG)` suffix), the `⚠` warning lines move to just under the `Rules:` line, and the 2014 `Multiplier:` line is always printed with `; excludes N not counted` in its parenthesis. That parenthesis is one flat list (owner ruling 2026-11-06): `×1.5 (2 monsters, stepped up — party fewer than 3; excludes 1 not counted)`, or `, stepped down — party larger than 5`, with no nested parentheses (this also changed the format when nothing is excluded). `Result:` is unchanged; with nothing counted the reply stays `No valid monsters provided…` plus the warnings
- `ddb_roll_treasure` accepts `treasure_type: "individual" | "hoard"`, `cr` or `monsters`, and `rules_edition` (default `"2024"`). Only 2024 tables exist, so the `Rules:` line under the title always names the 2024 DMG; `"2014"` adds "(no 2014 version exists — 2024 tables used)" and resolves monster CRs from 2014 stat blocks. The rules line is reserved up front like the coin trailer, so it survives any `maxOutputChars` truncation. Resolved names are tagged (`Goblin [2024] (CR 1/4)`)

- **Monster search quality** (B11, 2026-11-10; `src/tools/monster-search.ts` for the search, `src/tools/monster-service.ts` for the fetch layer and list cache, `src/name-match.ts` for the name predicate; `monster.ts` keeps get, stats and the stat block and re-exports the search).   - **Name rule.** An entry matches a typed `name` when the query occurs in its name at a word start (`matchesAtWordStart`: index 0, or right after a character that is not a letter or digit; a multi-word query must match as one run), or when it is in the typed name's twin group (`monsterTwin(entry) === monsterTwin(query)`). "goblin" lists Goblin Boss and "Goblin Warrior (Stranger Things)" but not Hobgoblin or the unrelated "… Warrior" hits the alias query used to bring in; "thug" still finds the 2024 Tough. Both names are folded first (R1, owner ruling 2026-11-10, `nameFold`): hyphens become spaces, straight and curly apostrophes are dropped, then `normalizeName`, so "will o wisp" matches Will-o'-Wisp. The alias spellings are still queried, but their other hits are dropped. Open5e does the same fold.
  - **Order (R5).** With a name, rows whose twin key equals the query's come first ("goblin" gives Goblin Warrior first, "thug" gives Tough), then A–Z (`en`), ties by id. Every other search is A–Z. Near matches keep D&D Beyond's relevance order.
  - **Candidates and paging (R2).** No name: the full cached list (of the book, with a `source`). A name: page 1 of each spelling. If every spelling has at most 500 hits (`NAME_SCAN_LIMIT`), a spelling that is more than its first page is read in full (`scanAllPages`); with more in any spelling, the name rules run over the full list instead, keeping each matching entry's whole twin group, so a common word ("dragon", 287 hits, is under the limit; a word with more than 500 is not) costs one cached full-list scan, in `ddb_search_site` too. On the paged name path (B1, owner ruling 2026-11-10), once the name rule has run, every other spelling of each match's twin group (`twinAliases`), less the spellings already queried and the matches' own names, has its page 1 fetched (at most one per rename pair, 8 at a time, same snapshot and asker) and only those twin groups' entries are merged, so "warrior" under 2014 lists Goblin [2014] (not Goblin Warrior) and under 2024 counts it as hidden; a failed spelling makes the result incomplete. Book and homebrew searches do no edition selection and skip it; the over-500 full-list path already keeps whole twin groups. A `type` or `size` that no known name contains answers no-match without fetching D&D Beyond's monster list (it still falls back to Open5e's not-found answer when no `source` is given). `source: "homebrew"` uses the unfiltered list with its fail-closed `isHomebrew !== false` check. One `SessionSnapshot` covers every page and spelling.

## parseCharacterData notes

- **Rules edition** (`src/tools/character/editions.ts`, phase 5; plan decisions 1–5, 9, 11 in the spec). The `Rules:` line and tags come from `characterRulesLine`, `classifyForEdition` and `characterTag` in `src/edition.ts`. (1) A definition that is non-Legacy, non-homebrew and lists a book in a 2024 category and one in a 2014 category (Dagger, Shield, Leather: one definition printed in both editions; 13 of the 15 live characters hold some) classifies as the character's main edition, with that edition's first book, so it is neither tagged nor listed. When the main edition is `unstated`, plain `classifyEdition` applies. (2) Within each ruleset group the line names everything except spells and items, which are counted (`8 spells, 27 items`); the inline tags name each one. The `homebrew` group names nothing: every kind is counted (`homebrew: 1 species, 1 feat, 2 spells`; order class, subclass, species, background, feat, spell, item), because homebrew names are other players' text and the line is not wrapped as untrusted. (3) A subclass is tagged and listed only when its ruleset differs from its class's; otherwise it inherits the class's tag.
