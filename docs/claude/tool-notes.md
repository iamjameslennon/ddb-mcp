# Tool behaviour reference

> Moved verbatim from `CLAUDE.md` on 2026-11-06 to keep that file lean. `CLAUDE.md` keeps the summary and links here; this file holds the full detail. Keep it current when behaviour changes.

## Tool notes

- `ddb_get_character` accepts a `sections` param — prefer `summary` or `combat` over `full` to save tokens. Every section opens with a `Rules:` line right after the character's name, which is wrapped as untrusted, so the Rules line follows the closing tag (part of `formatHeaderBlock`), and entries whose ruleset differs from the main edition carry an inline tag (see the Rules edition bullet under parseCharacterData notes). Character tools take no `rules_edition` and do no twin selection
- `ddb_character_lookup` tags every list line (the >3-hit list) with `editionTag` and gives every full hit a `rulesLine` under its first line, from the character's `CharacterEditions.info()` (so a Dagger on a 2014 character reads `Rules: 2014 · Basic Rules (2014)`). A homebrew hit (or a custom background's feature) is wrapped in `wrapIfHomebrew` / `wrapUntrusted`: the whole block, rules line included, or the whole list line, tag included. Class and subclass features take the owning class's or subclass's definition, racial traits the species, the background feature the background. No reason lines: character content has no requested edition. A spell's name falls back to the entry's `name` when its definition has none, and class spells are read from `classSpells[].classSpells` as the sheet does (it used to read only `spells`)
- `ddb_get_party` prints each member's `summary` section, so the header carries the `Rules:` line and the class, subclass, species and background tags; the head `Rules: edition not stated` covers unstated feats, spells and items there (carry-over (c), closed)
- `ddb_get_character_raw` returns raw 300–500 KB JSON and requires `confirm_large_response: true`
- `ddb_character_lookup` returns a summary list when >3 matches — refine the query to get full text
- `ddb_search_spells` / races / classes / backgrounds / feats / class_features / racial_traits all accept `limit` and `offset` for pagination
- **Open5e option-search fallbacks** (races, classes, backgrounds, feats) honour `limit` and `offset` (default 30/0), and the feats one honours `prerequisite` (case-insensitive substring of the prerequisite with its "Prerequisite:" prefix stripped; a feat with none never matches). The heading is `Found N feat(s) (SRD only):` when the page shows all N, else `…, showing A–B:` (offset > 0 included) with `*Use offset: B to see more.*` when more remain; an offset at or past the end is `Found N … (SRD only) — offset X is past the end.` (not the no-match reply). N counts every match; a single hit is still its detail block (owner ruling 2026-11-06)
- **Phase-3 tools** (`ddb_get_equipment`, `ddb_search_equipment`, `ddb_search_races`, `ddb_search_classes`, `ddb_search_backgrounds`, `ddb_search_feats`, `ddb_search_class_features`, `ddb_search_racial_traits`) take `rules_edition` (default `"2024"`) and `source`; `ddb_get_spell` / `ddb_search_spells` also take `source`, and `ddb_search_site` takes `rules_edition` only. `source` (slug, short name or title, resolved through `getSourceIndex()` to every matching id; `"homebrew"` is reserved and lists homebrew entries only, as on the monster tools) wins over `rules_edition`: no twin hiding, every entry in the book is listed with its tag, the header is `searchHeader({ sourceBook })`, and a `sourceNote` is added when the book's edition contradicts `rules_edition` (a get instead notes only when the shown entry's edition differs from `rules_edition`: `lookupSourceNote`, carry-over (ap)). Every search with results from D&D Beyond starts with its search header, then any note, then the tool's heading; the tag sits right after the bolded name (`- **Fighter** [2024] — …`); header totals and the footer ("N 2014 versions hidden — rules_edition: \"2014\" shows them") count the whole result after hiding, not just the page. In flat mode (spells, items, classes, backgrounds, feats) a twin group whose requested-edition pick fails the filters while the other edition's pick passes is not listed but is counted in the footer, once per group (`groupAndSelect`'s `countFilteredPicks`; monster search sets it too); when that leaves nothing listed, the reply is the search header, `No <kind> found matching the criteria.` and the footer, not an Open5e fallback.
- **Dual-edition items** (`ddb_get_equipment`, `ddb_search_equipment`, and the items section of `ddb_search_site`; decision 4, the rule character sheets use): a non-Legacy, non-homebrew item definition that lists a 2024-category and a 2014-category book (539 live, e.g. Longsword, Studded Leather) is classified as the requested edition, with that edition's first book (`classifyForEdition` in `src/edition.ts`, via `CatalogAdapter.dualEdition` in `edition-search.ts`). Under a `source` the book's edition decides when it is 2024 or 2014 (`source: "basic-rules-2014"` tags Longsword `[2014]`), else the requested edition. A dual item alone in its twin group (537 of 539) is shown under either edition with no reason line and is never counted as hidden. A non-dual entry of the requested edition beats a dual one (owner ruling 2026-10-28, option B): when the dual item's twin group holds one (the 2 live groups: Legacy Efficient Quiver with Quiver of Ehlonna, and Legacy and dual Robe of the Archmagi), the dual item classifies as `classifyEdition` does, so those groups print what they did before (`Efficient Quiver` under 2014 is the Legacy printing, `Rules: 2014 · Basic Rules (2014)`, with a "1 2024 version hidden" footer in search). Under a `source`, B looks only at the book's entries (B within the book, owner ruling 2026-10-29): the book's edition decides except where the Legacy twin is in the same book, so `source: "dmg-2014"` (which lacks Efficient Quiver) tags Quiver of Ehlonna `[2014]`, while under `basic-rules-2014` (which holds both Robes) the dual Robe stays `[2024]`. B counts only entries that pass the search's filters (under a `source` also the name filter, since that listing filters entry by entry): when a filter rejects the Legacy twin and passes the dual item, the dual item is listed with the requested edition's tag and is not counted as hidden. B tracks entries, not marker objects (`classifier()` in `edition-search.ts`). A dual pick's book note names its book in the requested edition. Item dedupe falls back to `entityTypeId:id`, then (both missing) to the id with the normalized name and filterType.
- **Book-choice note**: when one edition has several versions of an entry (a book owner's 2014 Goblin from Volo's and from Monsters of the Multiverse), the pick is official → non-Legacy → lowest id. Search lines name the book and the set-aside books (`· <book> (also in <book> — pass source to choose)`); a single get adds an "also in" line. For class features and racial traits the note goes on every line of a duplicated owner. Only set-aside versions that pass the search's filters count. `ddb_search_site` has no `source` param, so its sections omit the note (`bookNotes: false` → `SelectOptions`); lines keep their tag.
- **Class features and racial traits choose the edition per owner** (class, class + subclass, or species), not per feature, and filter first: under 2024, `class_name: "ranger"` lists only the 2024 Ranger, with the 2014 owner's features hidden and counted (no Natural Explorer, Primeval Awareness, Vanish); `name: "natural explorer"` finds `Natural Explorer [2014]`; Fighter `name: "ability score"` lists the 2024 lines (including level-prefixed ones like `6: Ability Score Improvement`) plus a hidden footer. Species group by base race: the 2024 Elf replaces the 2014 High Elf, Wood Elf and Eladrin (Variant) in `ddb_search_races` and `ddb_search_racial_traits`; `rules_edition: "2014"` lists each subrace; naming it (`race_name: "high elf"`) finds `High Elf [2014]` under either edition. A 2024 Bard who is a 2014 High Elf is served by naming the species, a per-call `rules_edition`, or `source`. Without `source`, results list the requested edition's owners first, then the other edition's (a 2014-only Samurai after every 2024 Fighter line), then third-party/homebrew/unstated owners, each band in the usual feature/trait order; species searches and the flat catalogs keep their plain order. In every mode, with or without `source`, entries that tie on that order (equal names: a 2024 "Tiefling" and a homebrew "Tiefling" subrace) are listed by the adapter's tiebreak, official → non-Legacy → lowest id.
- **`ddb_search_site`** with `category: "all"` prints one search header and one combined footer: each category contributes its `SearchSection` body, and the header appears only when at least one included section came from D&D Beyond. An Open5e section (`open5e: true`; built by the `o5Search*Section` siblings in `src/open5e.ts`, whose string wrappers `o5Search*` render them unchanged) keeps its own `Rules:` line (its header, or a single-hit detail block's own label) above its body, so an all-Open5e reply has no combined header. The combined footer counts the hidden twins of every section, D&D Beyond or Open5e, listed or dropped; no section prints its own footer, so a listed Open5e section's own hidden line moves into it (owner ruling 2026-11-02). A single category keeps its own header and footer. A section whose body is empty or that carries `noMatch` (never judged by its text) is dropped, including a hidden-only one, whose count still reaches the footer. When every section is dropped, the reply is `No results found for "<query>".`, followed by a blank line and the combined footer when any section hid twins (owner ruling 2026-11-02).
- `ddb_get_spell` / `ddb_search_spells` take `rules_edition` (default `"2024"`). Both editions are in the compendium (keyed by definition id); get shows the requested edition's spell with a `Rules:` line, or the other edition with a "no 2024/2014 version found" reason, and a rename line when the query used the other edition's name (`Acid Arrow` → Melf's Acid Arrow). Search hides the other edition's twins and tags each line.
- `ddb_get_spell` and `ddb_character_lookup` print `Casting Time:` through `castingTimeText` (`src/tools/casting-time.ts`), the one map of DDB's `activationType` (1 Action, 2 No Action, 3 Bonus Action, 4 Reaction plus `castingTimeDescription` as the trigger, 5/8 Special, 6 Minute, 7 Hour; other types print `N (activation type T)`). The label is plural when N is not 1; a missing or zero N counts as 1 and an absent `activation` reads `1 Action`. Before this, types 4 and 7 fell back to "Action" and 6 was labelled "Reaction". `actions.ts` still filters on the raw numbers.
- `ddb_search_rules` / `ddb_get_rules` — SRD rules search and retrieval, no login required. Both take `rules_edition` (default `"2024"`: SRD 5.2; `"2014"`: SRD 5.1). They read Open5e `/v2/rulesets/` (SRD 5.2: 11 chapters, SRD 5.1: 41, each nesting its sections), so a get takes a chapter name or slug (`Combat`, `combat`) or a section name (`Cover`, `Grappling`) and a chapter returns all its sections. A slug is the key after its first `_`. A get matches in the requested SRD first (exact chapter, exact section, partial chapter, partial section), then the other SRD with `(no matching 2024 rules section — 2014 text shown)`. A search lists matching chapters, naming matching sections, each tagged `[2024]` / `[2014]`, and when the requested SRD has no match lists the other SRD's under `(no matching 2024 rules sections — 2014 sections listed)`. Query and text are folded like `normalizeName`; a blank get name is not found and a blank search query lists every chapter. SRD 5.2 on Open5e has no Rules Glossary, so a 2024 `grapple` search falls back to 2014, and no spellcasting chapter, so a 2024 get of `spellcasting` returns the Spellcasting section of Multiclassing (the 2014 chapter needs `rules_edition: "2014"`). v1's 2014 Adventuring Gear, Conditions, Legal Information and Rest chapters no longer exist on this path
- `ddb_get_condition` takes `rules_edition` (default `"2024"`): the 2024 text is SRD 5.2.1 (`Exhaustion` is the 2024 text, with D20 Tests reduced), `"2014"` gives the six-level Exhaustion table. Both lines read `Rules: 2024 · SRD 5.2` / `Rules: 2014 · SRD 5.1`; there is no reason line or fallback, because both tables are vendored; an exact key wins, a partial name matching several conditions answers `Condition "ed" is ambiguous: … — use the full name.` (table order), and a unique partial resolves
- **Open5e fallbacks are final** (phase 4): every single lookup and single-hit detail block is labelled by its document's ruleset (`Rules: 2024 · SRD 5.2 (Open5e fallback — D&D Beyond unavailable | not found on D&D Beyond)` / `SRD 5.1`), with the usual reason line when the edition differs, while Open5e searches open with `open5eSearchHeader` and tag each line `[2024]` / `[2014]`; the interim `Rules: 2014 · SRD 5.1 (Open5e fallback — …)` label on every fallback is gone. An exact twin name in one SRD beats a partial match in the other, as on the D&D Beyond path, so `Rope` under 2014 gives SRD 5.2's Rope with `(no 2014 version found — 2024 text shown)` though SRD 5.1 has "Rope, hempen (50 feet)". Open5e `getMonsterStats` (`o5GetMonsterStats`) mirrors the D&D Beyond branch: exact twin name first, else partial matches grouped by twin key; one group is `found` (picked by edition), several are `ambiguous` with one candidate per group by CR then name, so a logged-out `Red Dragon` lists five candidates (Red Dragon Wyrmling, SRD 5.1's 2014-only Half-Red Dragon Veteran, Young, Adult and Ancient Red Dragon) and `Ancient Red` is found. Open5e monster blocks show recharge, per-day and legendary costs on action names, print `LEGENDARY_USES_NOTE` (`src/edition.ts`) on the line after `LEGENDARY ACTIONS` (v2 has no per-round count), and do not print v2 `subcategory`. `o5GetMonsterStats` selects the edition over every name match first; a picked record with an unknown CR is `not-found` for an exact or single-group match, never replaced by its other-edition twin; in an ambiguous list it stays, printed `<Name> (CR unknown)` (`CR_UNKNOWN_TEXT`, `src/edition.ts`) and sorted last, and when every pick is unknown the answer is `not-found`. `ambiguityMessage` (both paths) names at most `AMBIGUITY_LIST_CAP` (20) candidates in the caller's order (CR, then name), then `, and N more`. Open5e `school`, `type` and `size` match part of a word, untrimmed (so a whitespace-only query matches nothing), as on D&D Beyond; `rarity` stays exact and is trimmed on both paths; null `rarity` / `category` on an item record are tolerated (no empty parentheses; a magic item with a null rarity counts as Common). Open5e species searches group by base race, as D&D Beyond does. Seven armour renames (Leather, Padded, Studded leather, Hide, Half plate, Splint, Plate → "… Armor") apply to Open5e only
- **Open5e output details**: reaction spells show `reaction_condition` after "1 reaction", and `Duration:` is capitalized ("Instantaneous"); an item search with no match says "No items found matching the criteria (SRD only)." and a mundane item line is `• <name> [tag] (<category>)`; class `Features:` lists only `feature_type` CLASS_LEVEL_FEATURE; within the edition `selectByEdition` picks, an exact name beats endpoint order ("Plate Armor" under 2014 gives the SRD 5.1 items record); a weapon or armour get ends with its `items` twin's `Cost: … | Weight: …` line (same document, same Open5e twin key) when there is one; species and background detail blocks print the record's `desc` (SRD 5.1 only; SRD 5.2's are empty) before the traits or benefits; monster and item searches list 20 lines, then `*Refine your search to see more results.*` before the footer, as D&D Beyond's item search does; `rarity` matches exactly on both paths (`common` is not `Uncommon`), and mundane gear counts as Common (D&D Beyond: an item with no rarity; Open5e: every `items` record), so `rarity: "common"` lists mundane gear plus Common magic items; the `ddb_get_rules` `query` jump folds case, curly apostrophes and whitespace as the rules search does, keeping the original text; an ambiguous `ddb_get_condition` name lists at most 20 (`cappedList` in `src/edition.ts`, then ", and N more"; 15 conditions never reach it); `ddb_get_condition` matches only its own table keys (`constructor` is not found) and a blank name is not found
- `ddb_search_class_features` `class_name` matches the class or the subclass name (`champion` finds Champion features). Each owner gets its own entry, so a racial trait shared by a base race and its subraces (e.g. Darkvision under both High Elf and Wood Elf) is listed once per species — with `rules_edition: "2014"`, or when the subrace is named (`race_name: "high elf"`); by default the 2024 species hides the 2014 subraces of the same base race. A locked optional entry (`accessTypes` 4) is listed with a "locked — not available to this account" marker instead of text. When D&D Beyond returns no class or race data the tool errors with "… data is unavailable from D&D Beyond right now …"; "No class features / racial traits found matching …" means the data loaded and nothing matched, and ends with a reminder that D&D Beyond lists only the classes, subclasses and species available to your account, so an absent class or species may just be locked. `ddb_search_racial_traits` `race_name` also matches a subrace's base race: with `rules_edition: "2014"`, `elf` also finds "Eladrin (Variant)", a subrace of Elf (under the 2024 default the 2024 Elf replaces it, and the subrace is found by naming it)
- `ddb_read_book` defaults to 3000 chars; use `query` to jump to a specific heading. A `Rules:` line (`rulesLine` of the book's join, e.g. `Rules: 2024 · Player's Handbook (2024)`) sits between the `# <slug>` title and the `URL:` line; a book that doesn't join is `Rules: edition not stated`
- `ddb_list_library` stays JSON: each book gains `"edition": "[2024]"` (the `editionTag` text; `[edition not stated]` when the join fails). **Library join** (`librarySourceId` in `library.ts`): (a) the slug's non-empty path segments are tried right to left, each against the last non-empty segment of a source's `sourceURL`, and the first segment with any candidate decides the step (a pick, or a disagreement that falls through to (b); later segments are not tried), so a chapter path `dnd/phb-2024/creating-a-character` joins on `phb-2024` (`dnd/phb-2024` → `phb-2024`; a slug or `sourceURL` with no segment, `""` or null, never matches, because 57 sources have `sourceURL: ""`); (b) else the normalized title equals a source's normalized decoded `description` **or its book label** (`Player's Handbook (2024)`). Within a step the candidates are classified with `classifyEdition({ sourceId })`: non-`unstated` candidates that share one ruleset give the lowest id among them (`basic-rules-2014` is ids 1, 209, 210, 212, and 1 is the labelled one, so a Hidden Sources twin never wins); with no non-`unstated` candidate, the lowest id; if they disagree the step fails. Both steps failing is `{ ruleset: "unstated", book: null }`. `ddb_read_book` given a slug runs (a) only; when that fails and the title is unknown it fetches the library list once, takes the title of the library book whose slug equals the path or is a leading path prefix of it (the longest match wins; books with an empty slug are skipped) and runs (b). A slug missing from the library, or a failed library fetch, leaves the book "edition not stated" and never fails the read. Live 2026-10-23: 8 of 8 library books join by slug
- `ddb_rate_encounter` / `ddb_encounter_cr` accept `rules_edition: "2024" | "2014"` (default `"2024"`) for XDMG vs. classic DMG rules; `"2014"` also resolves named monsters' CRs from their 2014 stat blocks. Line 2 of the output is the `Rules:` line for that edition's Dungeon Master's Guide (`DMG_SOURCE_ID` in `src/edition.ts`), and each named monster carries an edition tag (`1 × Wolf [2024] (CR 1/4, 50 XP)`; a `cr`-supplied one has none)
- `ddb_roll_treasure` accepts `treasure_type: "individual" | "hoard"`, `cr` or `monsters`, and `rules_edition` (default `"2024"`). Only 2024 tables exist, so the `Rules:` line under the title always names the 2024 DMG; `"2014"` adds "(no 2014 version exists — 2024 tables used)" and resolves monster CRs from 2014 stat blocks. The rules line is reserved up front like the coin trailer, so it survives any `maxOutputChars` truncation. Resolved names are tagged (`Goblin [2024] (CR 1/4)`)
- `ddb_get_monster` / `ddb_search_monsters` take `rules_edition` (default `"2024"`). `ddb_get_monster` shows that edition's twin, the other edition with a reason line when it's the only one found, and, without a `source`, picks with the list response's `accessType` map (`{ "<id>": n }`, 4 = locked; a missing map or id = available): the first available entry of the requested edition, else an available other-edition twin with the `locked-2024` / `locked-2014` reason, else today's pick (both locked → Open5e, then the restricted block). The detail check (`accessType 4`, no stats) is the fallback when the map lacks the id or is wrong, with at most one extra detail request. With a `source`, a restricted pick is never swapped but gets a hint line naming a book with an official, available version (by short name when the book has no slug). `ddb_search_monsters` lists one entry per twin group (`groupAndSelect` with the same `available` predicate) and counts the other edition's hidden twins in its last line, including a group whose requested-edition pick fails the CR/type/size filters while the other edition's pick passes (`countFilteredPicks`, as in the catalogs; when that leaves nothing listed, the reply is the search header, `No monsters found matching the search criteria.` (with the same `(checked the first N of M entries)` note as the other no-match replies when the scan was partial) and the footer, not Open5e; a locked group's swapped pick is never counted); a swapped line ends with the locked suffix, a summary line before the footer counts swaps (a swapped group isn't hidden), and a header note counts entries that are locked (with or without `source`); both count every selected entry, as the header total does, not just the lines shown. A name search asks for 100 entries (monster-service's cap) per spelling. It queries every `twinAliases` spelling and merges by id. `source: "homebrew"` (case-insensitive, checked before book resolution) restricts both tools to homebrew entries, labelled homebrew, with no selection or swap; both page through up to 600 entries for it, and when D&D Beyond can't be used (logged out, or unreachable) they say so in a plain message instead of falling back to the Open5e SRD; `getMonsterStats` still skips homebrew. Both accept an optional `source` — a book's slug (`mm-2024`, `cos`, `basic-rules-2014`), short name, or title, resolved through the source index (`getSourceIndex()`: the live game config merged over `src/source-snapshot.ts`, so resolution survives a config outage) to *every* matching ID (slugs aren't unique) and filtered server-side via repeated `sources=` params, which also match reprints. Many 2014 core monsters (e.g. Zombie) are filed under `basic-rules-2014`, not `mm-2014`. An unknown source, or a book without that exact name, returns an error naming alternatives — never an Open5e or other-edition substitute; unowned content in the requested book returns DDB's restricted block with its ownership warning (Open5e is used only when DDB is unreachable, with a caveat). `source` wins over `rules_edition`: no twin selection reason, no locked-twin swap, and a search lists every entry in the book, tagged. When the book's edition contradicts `rules_edition` on a search, or the shown entry's edition does on a get (`sourceNoteFor` in `edition-search.ts`, `lookupSourceNote` in `src/edition.ts`; a 2024 reprint in a 2014 book reads `(source "cos" is a 2014 book, but this entry is 2024 text — shown whatever rules_edition says)`), a source note line says so. CR/type/size filters run client-side, so `searchMonsters` pages through up to 600 entries (monster-service caps `take` at 100) and says when it checked only part of the result set; the total is the largest any page reported, and never below the entries seen, so the header never reads "checked N of M" with N > M. A scan is still flagged partial when its totals agree with what was seen but it is known incomplete (a full first page whose reported total is below 100; a first page of exactly 100 reporting 100 is a genuine single page; a scan that reached the 600 cap is partial only when a total says there is more, so exactly 600 reads `checked 600 of 600`): the total then prints as `M+` (`checked 100 of 100+`, `Only the first 100 of 100+ were checked …`). A `cr` outside 0, 0.125, 0.25, 0.5, 1–30 returns `Unknown CR "999". Valid CRs: 0, 0.125, 0.25, 0.5, 1–30.` before either path runs (D&D Beyond used to skip the filter, Open5e to answer no matches). A name search whose spelling has more matches than the 100-entry cap adds `(the first 100 matches per name were checked)` after the `**Monster Search**` counts. **Logged out**, all three (`getMonster`, `searchMonsters`, `getMonsterStats`) ask monster-service through `anonymousFetch` (no credentials; after `ddb_logout` too: an anonymous asker skips the session checks around its fetch, `assertCurrentAfter` and the `bound` check of the available-sources hint, so the revoked flag no longer discards its answer or the hint, while authenticated requests keep the check and cache keys are fixed from the asker up front, carry-over (au)), with the CR/type/size tables from `getPublicGameConfig()` and labels from `getSourceIndex()` (built from the public config merged over the snapshot); anonymous answers are free content, everything else locked in the `accessType` map, so the locked/swap/restricted handling applies as for an account that owns no books, with logged-out wording from `src/edition.ts` (owner rulings 2026-11-02): the restricted block keeps its `Rules:` line and book and ends `*⚠️ Not logged in — run ddb_login if your account owns this content.*` (`LOGGED_OUT_RESTRICTED_NOTE`) instead of the ownership note; the search note, swap suffix and swap summary say "isn't available without logging in" (`lockedEntriesNote` / `lockedLineSuffix` / `lockedSwapSummary` with `loggedOut`), and the swap reason is `loggedOutReason` (`(not logged in, so the 2024 version isn't available — 2014 text shown; run ddb_login if your account owns it)`). Logged-in wording is unchanged. Logged out, a locked requested-edition entry whose twin in the other edition is free is **not** swapped when the requested edition's SRD has the creature by exact twin name (`o5MonsterInEdition`, which returns the record's AC, HP and stat block): `getMonster` returns that Open5e SRD text labelled `Rules: 2024 · SRD 5.2 (Open5e — the D&D Beyond version needs ddb_login)` (Open5e origin `needs-login`, also used for SRD 5.1 and for the logged-out restricted-block fallback; other fallbacks keep their labels; when that fallback finds only the other edition's SRD, `o5GetMonster`'s `lockedEdition` argument swaps the false `(no 2024 version found — 2014 text shown)` for the logged-out locked reason, `(not logged in, so the 2024 version isn't available — 2014 text shown; run ddb_login if your account owns it)`), and `searchMonsters` marks such groups available before `groupAndSelect` (`srdBackedGroups`), so the requested entry is listed (counted in the locked note, with the SRD record's AC and HP, since the locked list entry's are zeroed live) when it passes the filters, and counted as hidden when it fails one its twin passes; without SRD text (or when Open5e fails) the swap stays (owner's live probe: 8 such swaps in 6,001, one, Warhorse Skeleton, in SRD 5.2). The rule follows the requested edition, so under `rules_edition: "2014"` it asks SRD 5.1 (owner ruling 2026-11-02: kept). monster-service zeroes AC and HP on every locked list entry (logged out, or a logged-in account that doesn't own the book), so a printed search line for a locked entry whose AC and HP are both 0 shows the SRD record's (`o5MonsterInEdition`, the entry's own edition, exact name) or `AC —, — HP` when the SRD lacks it, Open5e fails, or the entry isn't 2014/2024 (`withListStats`, final review I1, owner ruling "SRD values, else dashes"); only the lines about to be printed are probed, after the filters, and unlocked entries print as before; an SRD record with a null AC or HP prints `—` for that part. `srdBackedGroups` probes only groups whose requested pick or an other-edition entry passes the CR/type/size filters (otherwise the group lists and counts nothing either way), so a filtered search that matches nothing asks Open5e nothing. `getMonsterStats` has no access map, so it takes the requested edition's own list CR whether or not the entry is locked: never the swap, never a guess. Only a failure (Open5e `unavailable`, with the source caveat) or an empty answer (Open5e `not-found`, as logged in) goes to Open5e; when both fail, the logged-out messages are the logged-in ones plus `NOT_LOGGED_IN_SUFFIX` (` (not logged in — ddb_login may show more)`). `source: "homebrew"` logged out still answers `Homebrew monster lookup requires login. ## parseCharacterData notes

- **Rules edition** (`src/tools/character/editions.ts`, phase 5; plan decisions 1–5, 9, 11 in the spec). The `Rules:` line and tags come from `characterRulesLine`, `classifyForEdition` and `characterTag` in `src/edition.ts`. (1) A definition that is non-Legacy, non-homebrew and lists a book in a 2024 category and one in a 2014 category (Dagger, Shield, Leather: one definition printed in both editions; 13 of the 15 live characters hold some) classifies as the character's main edition, with that edition's first book, so it is neither tagged nor listed. When the main edition is `unstated`, plain `classifyEdition` applies. (2) Within each ruleset group the line names everything except spells and items, which are counted (`8 spells, 27 items`); the inline tags name each one. The `homebrew` group names nothing: every kind is counted (`homebrew: 1 species, 1 feat, 2 spells`; order class, subclass, species, background, feat, spell, item), because homebrew names are other players' text and the line is not wrapped as untrusted. (3) A subclass is tagged and listed only when its ruleset differs from its class's; otherwise it inherits the class's tag. (4) Only what the sheet shows is classified and counted: every `char.feats` entry except `__INITIAL_ASI` (real feats and the `__DISGUISE_FEAT` entries in OTHER FEATURES), the spells the SPELLS section lists (deduped by definition id, else name), and the items it prints (every non-weapon plus equipped weapons), deduped the same way. Entries with no name are not counted, and nameless species, background and subclass entries are not listed; the printed output keeps its old empty slots for nameless class spells, items and weapons. Class features and racial traits are not classified (no sources of their own). A custom item (`definition.isCustomItem`) has no ruleset: no inline tag and not counted (B13, 2026-11-06). Item names are trimmed wherever they print (INVENTORY lists, EQUIPPED lines, weapon attack lines), before the tag is added, so `Q ` and `Q` merge. `data.customItems` stay unprinted: each mirrors an `isCustomItem` inventory entry (same id), already printed. (5) Placement: the line is in the header box on every section; tags sit right after the name (header race string, class, subclass, background; FEATS and OTHER FEATURES; spell names, duplicate warnings and CONCENTRATION SPELLS; EQUIPPED and INVENTORY entries; weapon attack lines, where the tag is padded with the name). (9) The parser takes the source index as a parameter instead of fetching it. (11) Classes always classify with plain `classifyEdition`. `entrySourceIds` ignores a non-array `sources`. `CharacterEditions.named(name, def)` is the one name-plus-tag helper (empty name, no tag). Live check 2026-10-23: all 15 characters differ from the phase-start code only by Rules lines and tags (one weapon line's padding includes its tag)
- **Racial traits list** (`buildRacialTraitLines`, `features.ts`): the sheet's RACIAL TRAITS skips a trait when `definition.hideInSheet === true`, `definition.displayConfiguration.RACIALTRAIT === 0`, or `requiredLevel` exceeds the total level (sum of `classes[].level`, so multiclass counts all classes). Identical rendered lines print once; the dedupe runs on the final, possibly wrapped string, so a homebrew trait never merges into an official one of the same name. Only this list is filtered: `ddb_character_lookup`, senses and granting entities still read every trait. Live fields confirmed on 152579009 and 112314883 (2026-11-06)
- **Senses**: collected from four sources — `type:"sense"` mods (2024), `type:"set"`/`type:"set-base"` mods (2014), `char.customSenses`, and `race.racialTraits[].definition.senses`. Deduplication keeps the highest value per sense. Two-pass model: pass 1 records baselines from `set`/`set-base`/customSenses/trait notes (each with its source componentId), pass 2 walks `type:"sense"` mods — same componentId as baseline = dual encoding (take max), different componentId = additive extension (e.g. Gloom Stalker Umbral Sight +30 ft on top of race darkvision).
- **Languages**: three storage mechanisms in DDB, all collected in `computeProficiencies`:
  1. `type:"language"` modifiers in `char.modifiers.*` — standard race/class/feat grants.
  2. `char.customProficiencies` entries with `type: 3` — player-added via "Custom Proficiency" UI; name is in the entry itself.
  3. `char.characterValues` entries with `typeId: 35` — `valueId` is a stringified integer pointing into the rule-data language table. Resolved client-side by DDB's React app via `/character/v5/rule-data` → `data.languages[]`. We mirror the ID→name lookup in `LANGUAGE_NAMES_BY_ID` (in `stats.ts`), 115 entries: the officially-sourced languages plus Telepathy. Unknown IDs fall back to `Language #N` so homebrew never silently disappears.
  - **Refreshing the language table**: run `npx tsx scripts/dump-sourced-languages.mts`. It fetches rule-data, filters for entries with `rpgSourceId != null`, and emits TypeScript-ready Record entries grouped by source. Paste the output into the `LANGUAGE_NAMES_BY_ID` block when DDB publishes a new sourcebook.
- **Refreshing the modifier subType table**: run `npx tsx scripts/dump-modifier-slugs.mts` (needs `ddb_login`). It rewrites `src/tools/character/modifier-slugs.ts` (commit it) from rule-data's tools, weapons, armor, weapon categories, languages, damage adjustments and conditions, plus its `HAND_ADDED` values. A subType missing from it prints on a wrapped `(custom)` line rather than disappearing.
- **Refreshing the source snapshot and rename table**: run `npx tsx scripts/dump-edition-renames.mts` (needs `ddb_login`; `--snapshot-only` needs no login). It rewrites `src/source-snapshot.ts` from the live game config (commit it), reports any `sourceCategoryId` missing from the category table in `src/edition.ts` (place it there by hand — unknown categories classify "edition not stated"), and prints 2014→2024 rename candidates with evidence. Add a pair to `src/edition-renames.ts` only after reading both descriptions, with the evidence in a comment.
- **Concentration**: `isConcentrationSpell(def)` in `reference.ts`. Precedence: (1) the definition's own boolean `concentration`; (2) the same definition id in the buffer or compendium; (3) the twin group's entry for the definition's own edition (`classifyEdition` against `peekSourceIndex()`, 2024 when not stated), via `selectByEdition` + `definitionTiebreak`; (4) `null`. `buildConcentrationByLevel` uses `isConcentrationSpell(def) ?? false`.
- **Ability scores**: `type:"set"` item modifiers (e.g. Amulet of Health) floor the calculated score; `type:"bonus"` modifiers (e.g. Ioun Stone) add to it.
- **Speed**: `type:"set"` overrides the base race speed; `type:"bonus"` modifiers (e.g. Longstrider, Boots of Speed) stack on top. Applies to walk/fly/swim/climb/burrow.
- **Spells**: cross-source duplicate detection flags spells granted by both `classSpells` (prepared/known) and `char.spells.*` (auto-granted). Warning line included in output.
- **Reactions**: `char.actions.*` entries with `activationType: 4` are shown in REACTIONS (e.g. Uncanny Dodge, Deflect Missiles).
- **Limited use**: `char.actions.*` entries with `limitedUse`, then every carried inventory item with rechargeable charges (`buildItemChargeLines` in actions.ts, carry-over (az)): `Consumable` and nameless items skipped, the reset printed as the `resetType` string or, for `Other`, the full `resetTypeDescription`. Homebrew lines in BONUS ACTIONS, REACTIONS and LIMITED USE are wrapped by their granting entity (`grantingEntities`, `withOptions`, `bucketAnyHomebrew`; F-2026-10-20). Array fields of the character JSON are read through `records()` (helpers.ts), so a null or non-object entry is skipped, not a crash.
- **Feats**: `__DISGUISE_FEAT` entries appear in OTHER FEATURES; `__INITIAL_ASI` entries (2024 background ASIs) are dropped entirely.
- **Text glitches** (B14, 2026-11-06): `helpers.stripHtml` decodes entities (`&mdash;`, `&rsquo;`, …) through `utils.stripHtml` before the whitespace collapse, so snippets, background features and notes print `—` and `’`; the decode runs before any `wrapUntrusted`, which scrubs delimiter text afterwards, so an entity-encoded delimiter in homebrew text is still neutralised. In `computeProficiencies` a **known** slug (`PROFICIENCY_SLUGS` / `LANGUAGE_SLUGS`) prints the modifier's `friendlySubtypeName` when non-empty (`Thieves' Tools`, `Thieves’ Cant`, `Crossbow, Light`), else the old capitalised slug; an unknown slug keeps the slug text on the wrapped custom line, since its friendly name is not D&D Beyond's. The lists are neither deduplicated nor sorted, so a name change reorders nothing. Character fetch errors: a 404 reads `Character <id> was not found (404) — check the ID, or that the character still exists.`; any other status is `D&D Beyond API returned <status>` with `: <statusText>` only when non-empty (the list error follows the same rule).
- **Templates**: `resolveTemplates()` supports `{{variable}}`, `{{variable*n}}`, `{{variable+n}}`, `{{variable-n}}`, `{{variable/n}}` with optional `#signed`/`#unsigned` suffix. Variables: `proficiency`, `level`, `characterlevel`, `classlevel`.
