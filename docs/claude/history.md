### Decisions

- **2024 by default, 2014 on request — for spells and monsters alike.** Every tool that can return either edition takes the same param: `rules_edition: "2024" | "2014"`, default `"2024"`. That is the name `ddb_rate_encounter` already uses; don't introduce `edition` or another spelling. Monster tools keep #58's `source` param as a separate book filter. When both are given, `source` wins, because a book is more specific than an edition.
- **#58 was merged rather than rewritten.** It already had deterministic 2024-by-default monster selection with a `preferLegacy` ranking hook, so the monster half of `rules_edition` builds on it. Every monster path now chooses with `selectByEdition`, over candidates ordered by `monsterTiebreak(index)` (official → Core Rules book → lowest ID): `getMonster` through `lookupByName` and `searchMonsters` through `groupAndSelect`, both with an `available` predicate built from the list response's `accessType` map; `getMonster` with a `source` and `getMonsterStats` call it directly, with no `available` predicate.
- **`getMonsterStats` never guesses.** It has no fuzzy fallback and skips homebrew, on both the DDB and Open5e paths. A wrong CR silently skews a rating or a treasure roll, while "not found (supply cr manually)" is recoverable. `getMonster` keeps its fuzzy fallback, because its output names the monster it shows.
- **Sequencing.** Rules-edition phase 3 is done (see [its plan](../../docs/superpowers/plans/2026-10-19-rules-edition-phase-3-equipment-options.md); item 0 and phase 2 too). Phase 4 is done (2026-10-21, commits `15e57e5..9d5ec31`, docs `124f658`/`c1ff944`, final-fix wave `e9f4e1a..9c629ba` and its docs commit; see [its plan](../../docs/superpowers/plans/2026-10-20-rules-edition-phase-4-open5e-v2-rules-conditions.md) and the rulings under phase 4 in the spec). Phase 5 is done (2026-10-23, commits `b705004..8ee84e3`, [plan](../../docs/superpowers/plans/2026-10-22-rules-edition-phase-5-characters-library.md); its rulings are under "Characters — phase 5" and "Library — phase 5" in the spec), so the `rules_edition` work is complete and the stateless-safe plan's Task 2 (`server.tool` → `registerTool`) is unblocked; Task 4 (delete `characterSpellBuffer`) is unblocked now that phase 2 is done. That plan's Task 1 (SDK floor `^1.30.0`) is already satisfied: `package.json` has `^1.32.2`, and 1.32.2 is installed.
- **Ambiguous partial monster names are reported, not resolved (item 3, done).** When a partial name like "Red Dragon" matches more than one distinct creature (Wyrmling / Young / Adult / Ancient, CR 4–24), `getMonsterStats` returns `ambiguous` and the encounter and treasure tools print `Ambiguous: "Red Dragon" could be … — use the full name.` with each candidate's name and CR, instead of picking one. Same reasoning as `getMonsterStats` never guessing: a wrong CR silently skews the result, an ambiguity message is recoverable. Edition twins of one creature (2014 vs 2024 "Zombie") are not ambiguous — `selectByEdition` picks between those, ordered by `monsterTiebreak(index)` (official → Core Rules → lowest ID).
- **Monster search hides edition twins (item 1).** Under the 2024 default, the 2014 entry of a twin group (same name, or linked by the rename table) is hidden when the group has a 2024 entry available to the account; 2014-only monsters stay listed. `rules_edition: "2014"` hides the 2024 twins instead. When the requested edition's entry is locked to the account and the other edition's isn't, the search swaps to the other edition's entry and says so (see the tool notes). This makes "2024 by default" mean the same thing in `ddb_search_monsters` as in `ddb_get_monster`. An explicit `source` filter shows whatever is in that book, with no twin hiding.
- **`source` contradicting `rules_edition` adds a note (item 1).** `source` still wins, but when the chosen book's edition differs from `rules_edition` (e.g. `source: "mm-2024"` with `rules_edition: "2014"`), a search says so in one line (exact wording is `sourceNote` in the rules-edition spec); a get says so when the entry it shows is not the `rules_edition` one (`lookupSourceNote`, carry-over (ap)). Not an error: the request is unambiguous, and an error just costs a round trip.
- **Phase 3 owner decisions (2026-10-19/20).** (1) Same-edition duplicates: official → non-Legacy → lowest id, and always name the book and the set-aside books, with `source` to choose. (2) `source` on every phase-3 tool and the spell tools (not on `ddb_search_site`, encounter, treasure, conditions or rules). (3) `ddb_search_classes` drops its dead "Subclasses:" line (item 6, removed). (4) Class features and racial traits choose the edition per owner (class, class + subclass, species), not per feature; third-party, homebrew and unstated owners are never hidden, and an owner with no version in the requested edition is listed with its own tag. (5) Filter first, then pick the owner. (6) Book-choice note on every line of a duplicated owner. (7) Species are edition-grouped by base race. (8) Subclasses renamed in 2024 get verified rename pairs (Draconic Bloodline → Draconic Sorcery, The Fiend → Fiend Patron, School of Evocation → Evoker, Way of the Open Hand → Warrior of the Open Hand); renames visible only to book owners stay a carry-over. (9) Every catalog search calls `getSourceIndex()`, not only those given a `source`. (10) `ddb_search_site` "all" prints the combined header only when at least one section came from D&D Beyond. Racial traits classify from the race's sources (the species decides the edition). Rulings after the plan (final review and carry-over round: filtered picks counted as hidden, book-note alternatives filtered, no book notes in `ddb_search_site`, requested edition first for features and traits, equal names by tiebreak, monster hidden-only reply, one in-flight game-config fetch) are in the spec's phase-3 section and the tool notes above.
- **Rules edition everywhere — see [docs/superpowers/specs/2026-10-16-rules-edition-design.md](../../docs/superpowers/specs/2026-10-16-rules-edition-design.md).** Every tool gives 2024 by default, 2014 only when it's the only version or `rules_edition: "2014"` is passed, and every response labels its ruleset (`Rules:` line or inline `[2024]`/`[2014]`/… tag). Labels are by book era (Xanathar's is "2014", with "no 2024 version found"); third-party/homebrew/playtest get their own label and are never hidden; character sheets get a summary line plus tags on minority-edition entries; Open5e fallbacks use v2 with SRD 5.2/5.1 (done in phase 4). Five phases, each written for a fresh agent. Where the spec and these bullets differ, the spec wins.
- **Fork security hardening is deferred, not rejected (2026-10-20).** See [Security findings](#security-findings). The gaps are real, but phases 4–5 still edit `src/tools/reference.ts` and the search formatters, and the stateless-safe plan's Task 2 onward rewrites the tool registrations in `src/server.ts`; porting now would create conflicts in both. 1. **Third-party OAuth cookies are persisted — Low/Medium.** `saveSession()` (`src/browser.ts:270`) writes `context.storageState()` whole. A Wizards ID login through Google or Apple leaves that provider's cookies and origin storage in `~/.config/ddb-mcp/session.json` (0600). The owner's current file is clean — 38 cookies, all on `dndbeyond.com`, one `www.dndbeyond.com` origin — because it did not use social login, so this is a code-path gap, not an observed incident.
