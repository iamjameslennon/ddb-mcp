# Caching layers

> Moved verbatim from `CLAUDE.md` on 2026-11-06 to keep that file lean. `CLAUDE.md` keeps the summary and links here; this file holds the full detail. Keep it current when behaviour changes.


- **Character JSON**: 60 s TTL in `character.ts`, keyed by session generation as well as cleared on invalidation. Anonymous-fallback results (token exchange failed) are never cached, so the next call retries with the token
- **Spells/items/compendium**: 24 h TTL in `reference.ts` (5 min when build was partial) — first spell call builds the full compendium by firing 16 parallel requests (`/game-data/spells` and `/game-data/always-known-spells`, `classLevel=20`, for each of the 8 spellcasting classes). Neither endpoint is complete alone: `/spells` returns only cantrips for prepared casters, and `always-known-spells` never returns cantrips. Results merge in fixed request order into an id-keyed `SpellStore` (`spell-store.ts`), first id wins, so both editions of a name are kept. Cached as `{ source, spells }` under `"spell-compendium-v2"`; the character-seeded `characterSpellBuffer` is keyed by definition id too
- **Class features / racial traits**: cache keys `"class-features"` / `"racial-traits"` in `reference.ts`, holding `{ source, entries }`: 24 h if every request succeeded, 5 min if any subclass or collection request failed (a cached partial build still prints the partial note). An empty or failed base list (`/classes`, `/races`) is never cached and the search says the data is unavailable. The classes and races lists are the same cached payloads (`game-data:classes` / `game-data:races`, via `loadGameDataList`) that `ddb_search_classes` / `ddb_search_races` use, so one fetch serves both tools
- **Open5e responses**: 1 h TTL in `open5e.ts`, one entry per document URL (at most 22) plus the shared equipment-split entry. Concurrent cold callers of one URL share a single in-flight fetch (`o5Pending`); a failed fetch is never cached as data, but its error is remembered for 60 s per URL (`o5Failures`, `O5_FAILURE_TTL_MS`) so an outage costs one attempt a minute per document, and joiners of a failing fetch all reject with it. One 30 s deadline covers all pages of a document (`O5_DOCUMENT_DEADLINE_MS`, combined with the 20 s per-request timeout), and an empty document, a first-page `count` above the records collected, or a response whose final URL is off `api.open5e.com` is rejected. The memo is written only while the fetch's `o5Pending` entry is still its own, like the cache write, and `clearOpen5eCache()` drops pending fetches too, so one that settles later doesn't repopulate the cache. `clearOpen5eCreatures()` (`ddb_clear_cache` `monsters`) drops just the two creature documents' cache entries, pending fetches and failure memos, with the same identity guard. The equipment split (the same-document guard over items, magicitems, weapons and armor in both documents) is computed once by concurrent cold callers (`equipmentSplitPending`) and cached only when all eight documents loaded and the computation is still the authoritative one (a `clearOpen5eCache()` mid-computation leaves nothing cached). A search (magicitems + items) whose weapons or armor document fails uses the split over the documents that loaded and answers anyway, uncached; a get (all four endpoints) still fails on any of them (owner ruling 2026-11-02)
- **Library list**: `fetchLibraryBooks()` in `library.ts` caches the parsed list for 60 s in a `TtlCache`, keyed by session generation, dropped by an `onSessionInvalidated` hook and by `ddb_clear_cache` `all`; an empty parse and failures are never cached, and a fetch that finishes after the session changed throws `SessionChangedError` to its caller and every joiner (never the old account's list); a result is cached only while its fetch is still the authoritative `libraryPending` entry, so `ddb_clear_cache` or a session transition mid-fetch leaves nothing cached. Concurrent cold callers of one generation share one in-flight fetch (`libraryPending`, cleared on settle, never joined across generations, dropped by the hook). `resolveBookSlug` uses it untagged, so a title read fetches the library once and the source index once.
- **Game config / source index**: `game-config.ts` caches the config until the next session transition (a failed fetch is remembered for 60 s per session — `CONFIG_FAILURE_TTL_MS`, so an outage costs one ~7 s retry run a minute, not one per call, and a late failure from an old session records nothing; a rejected one is never cached). Concurrent cold callers of one session generation share one in-flight fetch (`configPending`, modelled on the cobalt-token `cobaltTokenPending`): the entry is published before the fetch starts, a newer generation never joins an older one's fetch, a settlement (either way) clears only its own entry, the invalidation hook drops it, a session change before the fetch runs sends no request, and every joiner gets the starter's result — the config, or null. A deadline bounds the fetch: `CONFIG_FETCH_TIMEOUT_MS` (10 s) aborts it, resolves every caller null, releases the slot and remembers the failure for `CONFIG_FAILURE_TTL_MS`; the aborted fetch's late settlement records nothing. Catalog searches, `parseCharacter`, `getParty` and `getDefinition` start `getSourceIndex()` alongside their data load instead of after it (never under `source: "homebrew"`), passing an `AbortSignal` they abort when the load fails (or `getParty`'s campaign has no characters), since nothing will read that index: `getGameConfig({ signal })` counts its waiters, a withdrawn caller resolves null at once (`getSourceIndex` → `peekSourceIndex()`), and when the last waiter withdraws the shared fetch is aborted, before dispatch when it hasn't been sent, with no further retries and no deadline; it records the 60 s failure memo only if an attempt had already failed (an HTTP error, seen through `sessionFetch`'s `onResponse` hook, or a network error), so an outage still costs about one attempt a minute, and a fetch cancelled before any failure records nothing (an old session or a clear records nothing either); a caller without a signal keeps it alive. A session file holding only session cookies (or expired persistent ones) makes `hasValidSession()` false, so monster lookups run anonymously; `getGameConfig()` then returns `getPublicGameConfig()` (no Cookie header) instead of sending the cookies; with no session file `getGameConfig()` still sends nothing, but `getSourceIndex()` (no valid session) asks `getPublicGameConfig()`, so logged out, catalog searches, public characters and `getDefinition` send one anonymous config request per session (cached until the next session transition, 60 s failure memo; the withdrawn-caller path of `publicConfigUntilAborted` takes `peekSourceIndex()` at once). A logged-out character call (`parseCharacter`, `getDefinition`) passes `loggedOutWaitMs: LOGGED_OUT_CHARACTER_INDEX_WAIT_MS` (2 s): with no valid session it stops waiting for the public config after that long and uses `peekSourceIndex()`, a withdrawal that leaves the shared public fetch running (it fills the cache for the next call, records no failure memo, and the caller's abort listener is removed); a valid session keeps the 10 s deadline, even when the cobalt exchange is then rejected (owner ruling 2026-11-04). An index build writes `indexCache` only if its path's epoch is unchanged (`configEpoch`, or `publicConfigEpoch`, bumped by `clearPublicGameConfig()`), so a fetch that settles after `ddb_clear_cache` doesn't repopulate it. One `SourceIndex` is cached per config object, so a newly fetched config rebuilds the index. `peekSourceIndex()` is the synchronous, never-fetching variant: it returns the cached index, else a memoized snapshot-only one. `getPublicGameConfig()` (logged-out monster lookups) has its own cache, one in-flight fetch, the same 10 s deadline and a 60 s failure memo. All of this is dropped by the module's `onSessionInvalidated` hook, and `ddb_clear_cache` (`monsters` / `all`) drops the config, its index, the failure memo and any pending fetch through `clearGameConfig()` (a fetch that settles after the clear writes neither the cache nor the memo: `configEpoch`), alongside `clearPublicGameConfig()`
- **Cobalt JWT**: cached in-memory until 60 s before expiry, stamped with the generation it was minted under (`session-fetch.ts`). Concurrent cache misses in one generation share a single in-flight `POST /v1/cobalt-token` (`cobaltTokenPending`), so a cold compendium build's 16 parallel requests send one exchange, not 16. The entry is published before the mint runs, dropped by the invalidation hook, and cleared when it settles, so failures are never cached. A settlement clears only its own entry, and callers compare generations before joining, so a newer generation never joins or loses an older one's exchange. Every caller, starter and joiners alike, re-checks authority after the exchange settles. The timeout is abort-based. A 30 s deadline (`COBALT_TOKEN_TIMEOUT_MS`), started once per exchange, aborts the exchange's signal, which cuts short dispatch, retry backoff and the body read with `CobaltTokenTimeoutError`. The same deadline releases the pending slot, so later callers start afresh even if a step ignored the abort. Callers stuck on such a step stay stuck. The trade-off: one failure or timeout fails every joined caller together, so a cold compendium build falls back as a whole rather than ending up partial. Retry backoff in `fetchWithRetry` wakes early when the merged signal aborts; a session change still surfaces as `SessionChangedError`
- **Session cookies**: in-memory after first disk read; invalidated by `invalidateSessionCache()` when a new session is saved, and by `revokeSession()` (`ddb_logout`)
- **Monster lists and stat blocks**: 24 h in `monster.ts`; logged-out (anonymous) answers are cached under `anon:`-prefixed keys, since their `accessType` map differs, so they never serve a logged-in call or the reverse
- **Every account-derived cache** (character JSON, spells/compendium, class features / racial traits, monster stat blocks, campaigns) registers an `onSessionInvalidated()` hook and is dropped on any session transition — login, account swap, or `ddb_logout` — not just on its own TTL expiry
