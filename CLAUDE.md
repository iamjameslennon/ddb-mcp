## Architecture

This is a [Model Context Protocol](https://modelcontextprotocol.io) (MCP) server that exposes D&D Beyond data to Claude via stdio transport. Entry point: `src/index.ts` (stdio transport, signal handlers, `main()`). All MCP tools are registered in `src/server.ts`, which exports the `McpServer` (built with `SERVER_INSTRUCTIONS` from `src/edition.ts`), and delegate to modules in `src/tools/`.

### Two execution paths: browser vs. browserless

The central architectural split is between tools that need a Playwright browser and tools that work entirely through the saved session cookies:

**Browserless (preferred)** — `src/session-fetch.ts`
- Reads cookies from a per-user config dir — `~/.config/ddb-mcp/session.json` on macOS/Linux, `%APPDATA%\ddb-mcp\session.json` on Windows (written by `ddb_login`)
- Exchanges cookies for a short-lived cobalt JWT via `getCobaltToken()`
- All character, monster, spell, item, and condition tools use this path
- `sessionFetch()` injects the cookie header into native Node `fetch` — cookies only, no Bearer token
- `anonymousFetch()` is the credential-free path for public endpoints used while logged out (monster-service, the game config): no Cookie, no Authorization, never reads the session, the same retry policy, and a 20 s deadline (`ANONYMOUS_FETCH_TIMEOUT_MS`) over all retries and the body read
- character-service (`/character/v5/character/{id}`, `/characters/list`) ignores cookies and requires the cobalt Bearer token — use `beginAuthenticatedSession()`, whose bound `fetch` sends the token and cookies from one snapshot. Never pair a separate `getCobaltToken()` with `sessionFetch()`: each captures its own snapshot, so an account swap between them can send one account's token with another's cookies
- Every credential access binds to a `SessionSnapshot` from `src/session-state.ts` (see **Revocable session lifecycle** below) and re-checks on-disk authority before dispatch — a deleted/replaced session file, or a `ddb_logout` revoke, stops the old account's credentials at the next protected operation with no explicit invalidation call required

**Browser-based (Playwright)** — `src/browser.ts`
- Required for: `ddb_login` (OAuth flow, visible window), `ddb_navigate`, `ddb_interact`, `ddb_get_page` (every other tool is browserless — see [Browser dependencies](#browser-dependencies))
- Singleton browser/context (`getBrowser` / `getContext`) — lazy-initialized, shared across calls, bound to the generation they were opened under (an `onSessionInvalidated` hook closes and detaches the shared context/browser on every session transition, including a `ddb_logout` revoke — `revokeSession()` awaits that close and reports if it fails)
- `ddb_login` forces `headless: false`; all other browser tools use `headless: true`
- navigate/interact/get_page leave the browser open intentionally; `ddb_close_browser` (or process shutdown in `index.ts`) closes it
- Login uses a deliberately separate browser/context (`beginLoginSession()`/`endLoginSession()`) from the shared authenticated one, so a login can't reuse a possibly-revoked context and a revoke mid-login can't be raced into recreating a just-deleted session (`saveSession()` re-checks the generation it began under)

### Revocable session lifecycle — `src/session-state.ts`

Owns the single authoritative answer to "which account are we, right now?" and sits below every other module (never imports a tool module). A "generation" is an opaque, process-local, monotonically-increasing token; two `SessionSnapshot`s share a generation iff they describe the same on-disk session-file content. `captureSession()` re-reads the file on every call — this re-read, not a file watcher or mtime check, is what makes deletion/replacement/corruption observed at the next protected operation. Any observed change advances the generation, aborts in-flight work (via `AbortSignal`), detaches cached state, and fires every callback registered with `onSessionInvalidated()` (session-fetch's cobalt-JWT cache, `browser.ts`'s shared context/browser, and each tool module's account-derived cache all register one).

`revokeSession()` — the primitive behind `ddb_logout` — blocks new authenticated operations immediately (`revoked` flag, checked before any file read), invalidates in-memory state, deletes the saved session file (`rmSync(..., { force: true })`, ENOENT-safe), then `Promise.allSettled`s every registered async cleanup hook (currently just the browser close) before resolving. Repeated calls are idempotent. If file deletion or a cleanup hook throws, `revokeSession()` still leaves the process-local `revoked` flag set — no old-file reload, no silent "logout succeeded" — and rejects with an `Error` naming which step failed. A subsequent `ddb_login` clears the flag via `invalidateSessionCache() → clearRevoked()`, establishing fresh authority. See [README's Logging out section](README.md#logging-out) for the user-facing guarantee and its limits (detection is at the next protected operation, not instantaneous; stop the process for immediate termination).

**Future design note:** any later stateless-safe/browser-factory redesign must adopt this same lifecycle rather than reinvent it — factory-created browsers need to bind each created context to a captured `SessionSnapshot` and register the same kind of `onSessionInvalidated` revocation hook `browser.ts` uses today, and any future on-disk cache (e.g. a persisted spell compendium) needs a durable per-account/session key plus validation at read time, not the in-memory `generation` counter alone — it's process-local and resets on restart, so it cannot identify which account a given disk-cache entry belongs to across process restarts.

### Caching layers

- **Character JSON**: 60 s TTL in `character.ts`, keyed by session generation as well as cleared on invalidation. Anonymous-fallback results (token exchange failed) are never cached, so the next call retries with the token
- **Spells/items/compendium**: 24 h TTL in `reference.ts` (5 min when build was partial) — first spell call builds the full compendium by firing 16 parallel requests (`/game-data/spells` and `/game-data/always-known-spells`, `classLevel=20`, for each of the 8 spellcasting classes). Neither endpoint is complete alone: `/spells` returns only cantrips for prepared casters, and `always-known-spells` never returns cantrips. Results merge in fixed request order into an id-keyed `SpellStore` (`spell-store.ts`), first id wins, so both editions of a name are kept. Cached as `{ source, spells }` under `"spell-compendium-v2"`; the character-seeded `characterSpellBuffer` is keyed by definition id too
- **Class features / racial traits**: cache keys `"class-features"` / `"racial-traits"` in `reference.ts`, holding `{ source, entries }`: 24 h if every request succeeded, 5 min if any subclass or collection request failed (a cached partial build still prints the partial note). An empty or failed base list (`/classes`, `/races`) is never cached and the search says the data is unavailable. The classes and races lists are the same cached payloads (`game-data:classes` / `game-data:races`, via `loadGameDataList`) that `ddb_search_classes` / `ddb_search_races` use, so one fetch serves both tools
- **Open5e responses**: 1 h TTL in `open5e.ts`, one entry per document URL (at most 22). Concurrent cold callers of one URL share a single in-flight fetch (`o5Pending`); a failed fetch is never cached as data, but its error is remembered for 60 s per URL (`o5Failures`, `O5_FAILURE_TTL_MS`) so an outage costs one attempt a minute per document, and joiners of a failing fetch all reject with it. One 30 s deadline covers all pages of a document (`O5_DOCUMENT_DEADLINE_MS`, combined with the 20 s per-request timeout), and an empty document, a first-page `count` above the records collected, or a response whose final URL is off `api.open5e.com` is rejected. The memo is written only while the fetch's `o5Pending` entry is still its own, like the cache write, and `clearOpen5eCache()` drops pending fetches too, so one that settles later doesn't repopulate the cache
- **Library list**: `fetchLibraryBooks()` in `library.ts` caches the parsed list for 60 s in a `TtlCache`, keyed by session generation, dropped by an `onSessionInvalidated` hook and by `ddb_clear_cache` `all`; an empty parse and failures are never cached, and a fetch that finishes after the session changed throws `SessionChangedError` to its caller and every joiner (never the old account's list); a result is cached only while its fetch is still the authoritative `libraryPending` entry, so `ddb_clear_cache` or a session transition mid-fetch leaves nothing cached. Concurrent cold callers of one generation share one in-flight fetch (`libraryPending`, cleared on settle, never joined across generations, dropped by the hook). `resolveBookSlug` uses it untagged, so a title read fetches the library once and the source index once.
- **Game config / source index**: `game-config.ts` caches the config until the next session transition (a failed fetch is remembered for 60 s per session — `CONFIG_FAILURE_TTL_MS`, so an outage costs one ~7 s retry run a minute, not one per call, and a late failure from an old session records nothing; a rejected one is never cached). Concurrent cold callers of one session generation share one in-flight fetch (`configPending`, modelled on the cobalt-token `cobaltTokenPending`): the entry is published before the fetch starts, a newer generation never joins an older one's fetch, a settlement (either way) clears only its own entry, the invalidation hook drops it, a session change before the fetch runs sends no request, and every joiner gets the starter's result — the config, or null. A deadline bounds the fetch: `CONFIG_FETCH_TIMEOUT_MS` (10 s) aborts it, resolves every caller null, releases the slot and remembers the failure for `CONFIG_FAILURE_TTL_MS`; the aborted fetch's late settlement records nothing. Catalog searches, `parseCharacter`, `getParty` and `getDefinition` start `getSourceIndex()` alongside their data load instead of after it (never under `source: "homebrew"` in `searchOwnedEntries`). One `SourceIndex` is cached per config object, so a newly fetched config rebuilds the index. `peekSourceIndex()` is the synchronous, never-fetching variant: it returns the cached index, else a memoized snapshot-only one. `getPublicGameConfig()` (logged-out monster lookups) has its own cache, one in-flight fetch, the same 10 s deadline and a 60 s failure memo. All of this is dropped by the module's `onSessionInvalidated` hook
- **Cobalt JWT**: cached in-memory until 60 s before expiry, stamped with the generation it was minted under (`session-fetch.ts`). Concurrent cache misses in one generation share a single in-flight `POST /v1/cobalt-token` (`cobaltTokenPending`), so a cold compendium build's 16 parallel requests send one exchange, not 16. The entry is published before the mint runs, dropped by the invalidation hook, and cleared when it settles, so failures are never cached. A settlement clears only its own entry, and callers compare generations before joining, so a newer generation never joins or loses an older one's exchange. Every caller, starter and joiners alike, re-checks authority after the exchange settles. The timeout is abort-based. A 30 s deadline (`COBALT_TOKEN_TIMEOUT_MS`), started once per exchange, aborts the exchange's signal, which cuts short dispatch, retry backoff and the body read with `CobaltTokenTimeoutError`. The same deadline releases the pending slot, so later callers start afresh even if a step ignored the abort. Callers stuck on such a step stay stuck. The trade-off: one failure or timeout fails every joined caller together, so a cold compendium build falls back as a whole rather than ending up partial. Retry backoff in `fetchWithRetry` wakes early when the merged signal aborts; a session change still surfaces as `SessionChangedError`
- **Session cookies**: in-memory after first disk read; invalidated by `invalidateSessionCache()` when a new session is saved, and by `revokeSession()` (`ddb_logout`)
- **Monster lists and stat blocks**: 24 h in `monster.ts`; logged-out (anonymous) answers are cached under `anon:`-prefixed keys, since their `accessType` map differs, so they never serve a logged-in call or the reverse
- **Every account-derived cache** (character JSON, spells/compendium, class features / racial traits, monster stat blocks, campaigns) registers an `onSessionInvalidated()` hook and is dropped on any session transition — login, account swap, or `ddb_logout` — not just on its own TTL expiry

### parseCharacterData notes

- **Rules edition** (`src/tools/character/editions.ts`, phase 5; plan decisions 1–5, 9, 11 in the spec). The `Rules:` line and tags come from `characterRulesLine`, `classifyForEdition` and `characterTag` in `src/edition.ts`. (1) A definition that is non-Legacy, non-homebrew and lists a book in a 2024 category and one in a 2014 category (Dagger, Shield, Leather: one definition printed in both editions; 13 of the 15 live characters hold some) classifies as the character's main edition, with that edition's first book, so it is neither tagged nor listed. When the main edition is `unstated`, plain `classifyEdition` applies. (2) Within each ruleset group the line names everything except spells and items, which are counted (`8 spells, 27 items`); the inline tags name each one. The `homebrew` group names nothing: every kind is counted (`homebrew: 1 species, 1 feat, 2 spells`; order class, subclass, species, background, feat, spell, item), because homebrew names are other players' text and the line is not wrapped as untrusted. (3) A subclass is tagged and listed only when its ruleset differs from its class's; otherwise it inherits the class's tag. (4) Only what the sheet shows is classified and counted: every `char.feats` entry except `__INITIAL_ASI` (real feats and the `__DISGUISE_FEAT` entries in OTHER FEATURES), the spells the SPELLS section lists (deduped by definition id, else name), and the items it prints (every non-weapon plus equipped weapons), deduped the same way. Entries with no name are not counted, and nameless species, background and subclass entries are not listed; the printed output keeps its old empty slots for nameless class spells, items and weapons. Class features and racial traits are not classified (no sources of their own). (5) Placement: the line is in the header box on every section; tags sit right after the name (header race string, class, subclass, background; FEATS and OTHER FEATURES; spell names, duplicate warnings and CONCENTRATION SPELLS; EQUIPPED and INVENTORY entries; weapon attack lines, where the tag is padded with the name). (9) The parser takes the source index as a parameter instead of fetching it. (11) Classes always classify with plain `classifyEdition`. `entrySourceIds` ignores a non-array `sources`. `CharacterEditions.named(name, def)` is the one name-plus-tag helper (empty name, no tag). Live check 2026-10-23: all 15 characters differ from the phase-start code only by Rules lines and tags (one weapon line's padding includes its tag)
- **Senses**: collected from four sources — `type:"sense"` mods (2024), `type:"set"`/`type:"set-base"` mods (2014), `char.customSenses`, and `race.racialTraits[].definition.senses`. Deduplication keeps the highest value per sense. Two-pass model: pass 1 records baselines from `set`/`set-base`/customSenses/trait notes (each with its source componentId), pass 2 walks `type:"sense"` mods — same componentId as baseline = dual encoding (take max), different componentId = additive extension (e.g. Gloom Stalker Umbral Sight +30 ft on top of race darkvision).
- **Languages**: three storage mechanisms in DDB, all collected in `computeProficiencies`:
  1. `type:"language"` modifiers in `char.modifiers.*` — standard race/class/feat grants.
  2. `char.customProficiencies` entries with `type: 3` — player-added via "Custom Proficiency" UI; name is in the entry itself.
  3. `char.characterValues` entries with `typeId: 35` — `valueId` is a stringified integer pointing into the rule-data language table. Resolved client-side by DDB's React app via `/character/v5/rule-data` → `data.languages[]`. We mirror the ID→name lookup in `LANGUAGE_NAMES_BY_ID` (in `stats.ts`), covering all 115 officially-sourced languages plus Telepathy. Unknown IDs fall back to `Language #N` so homebrew never silently disappears.
  - **Refreshing the language table**: run `npx tsx scripts/dump-sourced-languages.mts`. It fetches rule-data, filters for entries with `rpgSourceId != null`, and emits TypeScript-ready Record entries grouped by source. Paste the output into the `LANGUAGE_NAMES_BY_ID` block when DDB publishes a new sourcebook.
- **Refreshing the source snapshot and rename table**: run `npx tsx scripts/dump-edition-renames.mts` (needs `ddb_login`; `--snapshot-only` needs no login). It rewrites `src/source-snapshot.ts` from the live game config (commit it), reports any `sourceCategoryId` missing from the category table in `src/edition.ts` (place it there by hand — unknown categories classify "edition not stated"), and prints 2014→2024 rename candidates with evidence. Add a pair to `src/edition-renames.ts` only after reading both descriptions, with the evidence in a comment.
- **Concentration**: `isConcentrationSpell(def)` in `reference.ts`. Precedence: (1) the definition's own boolean `concentration`; (2) the same definition id in the buffer or compendium; (3) the twin group's entry for the definition's own edition (`classifyEdition` against `peekSourceIndex()`, 2024 when not stated), via `selectByEdition` + `definitionTiebreak`; (4) `null`. `buildConcentrationByLevel` uses `isConcentrationSpell(def) ?? false`.
- **Ability scores**: `type:"set"` item modifiers (e.g. Amulet of Health) floor the calculated score; `type:"bonus"` modifiers (e.g. Ioun Stone) add to it.

- **Feats**: `__DISGUISE_FEAT` entries appear in OTHER FEATURES; `__INITIAL_ASI` entries (2024 background ASIs) are dropped entirely.
- **Templates**: `resolveTemplates()` supports `{{variable}}`, `{{variable*n}}`, `{{variable+n}}`, `{{variable-n}}`, `{{variable/n}}` with optional `#signed`/`#unsigned` suffix. Variables: `proficiency`, `level`, `characterlevel`, `classlevel`.

### Release process

Releases are automated via `scripts/release.js` (ES module, Node built-ins only):

1. Guards: clean tree, on `main`, and not behind `origin/main` (a failed `git fetch` downgrades to a warning). Each guard warns instead of exiting under `--dry-run`
2. Resolves the `claude` binary by scanning `~/.local/share/mise/installs/node/*/bin/claude` — no shim needed
3. Runs `npm ci && npm test` before anything is written, so a broken tree can't earn a permanent tag and a public release. `npm ci` runs `prepare` (= `npm run build`), so this compiles `dist/` too. Skipped by `--dry-run`, or by `--skip-verify` when you've just run it yourself
4. Collects git log and diff since last tag; calls `claude -p` to generate plain-English release notes for DMs/players
5. Prompts for confirmation, then bumps `version` in `package.json` and `package-lock.json` directly, and rewrites the `@iamjameslennon/ddb-mcp@X.Y.Z` pins in `README.md`
6. Commits as `chore: release vX.Y.Z`, pushes tag, creates GitHub release via `gh`
7. The `npm-publish.yml` workflow triggers on GitHub release and publishes to npm using OIDC Trusted Publishing (`--provenance`, no `NPM_TOKEN` secret required)
8. Finally, best effort and never fatal: regenerates `lhm.plugin.json` and publishes the new version to the LobeHub Marketplace (see below). It runs last on purpose — the tag, GitHub release, and npm publish have all already succeeded, so a marketplace failure only warns and prints the two commands to re-run

### CI / CD

- `.github/workflows/ci.yml` — runs on push/PR to `main`, three jobs: **Type Check, Lint & Build** (matrix: Node 22/24/26 — `npm ci` runs `prepare` so the install *is* the build; then typecheck → lint → test), **Security Audit** (`--omit=dev` gates the release; a second dev-inclusive audit is informational and never fails), and **Lint Workflows** (actionlint, pinned by version + SHA256, with a hard precondition that `shellcheck` is present — actionlint skips shell linting *silently* without it)

### Container / MCP directory builds

`Dockerfile` at the repo root exists for MCP directories (Glama et al.), which build from a maintainer-authored Dockerfile when one is checked in and otherwise infer one with an LLM. Two-stage: stage 1 runs `npm ci` (whose `prepare` hook is the `tsc` build), stage 2 runs `npm ci --omit=dev --ignore-scripts` and copies `dist/` across. Runs as the unprivileged `node` user with `DDB_NO_SANDBOX=1`; `CMD` is the plain stdio server (`node dist/index.js`) — hosts needing HTTP/SSE wrap it themselves.

Two traps this exists to avoid, both from Glama's inferred build using **pnpm**:

1. **Undeclared transitive imports.** npm's flat `node_modules` resolves them; pnpm's strict layout does not. `domhandler` (a cheerio dep, imported by [src/tools/library.ts](src/tools/library.ts)) was undeclared and broke the build while `npm ci` and CI stayed green. Every non-builtin import needs its own `package.json` entry.
2. **`overrides` is npm-only.** pnpm reads `pnpm.overrides`, so the production-audit pins silently vanish under pnpm. Both blocks are present and **must be kept in sync**.

`.dockerignore` keeps `dist/` and `node_modules/` out of the context so the image's `dist/` always comes from its own `tsc` run. `glama.json` (`maintainers`) claims the directory listing.

### Browser dependencies

All content tools are now browserless. `ddb_search_site` ([search.ts](src/tools/search.ts)) delegates to the cached compendia in `reference.ts` / `monster.ts`. `ddb_list_library` ([library.ts](src/tools/library.ts)) parses the library page's embedded RSC payload (`self.__next_f.push(…)` chunks) from `sessionFetch` HTML. `ddb_read_book` fetches sourcebook pages via `sessionFetch` and walks the `<article>` tree with cheerio — DDB book chapters are server-rendered, so no JS execution is needed.

The only tools that still drive a browser are `ddb_login`, `ddb_navigate`, `ddb_interact`, and `ddb_get_page` — all inherently browser-bound (OAuth flow / live page interaction).

Browser contexts used by navigate/interact/get_page carry a navigation guard (`ensureNavigationGuard` in [navigate.ts](src/tools/navigate.ts)): top-level navigations to non-allowlisted hosts are aborted at the network layer, `interact` re-checks `page.url()` after every click, and `getCurrentPageContent` refuses to scrape any page outside the allowlist (covers data:-URL navigations, which never hit the network layer). The `ddb_login` context never passes through these functions, so the Wizards SSO redirect flow stays unguarded.
